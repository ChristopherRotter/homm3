# Open questions

Questions waiting for the user. Agents add new ones here (context, options, recommendation, what is blocked). When answered, record the decision (ADR or doc) and move the entry to "Answered".

Since Phase 0 (2026-10-07) every lane adds its questions here with a lane id that counts per lane: `BAT-Q1`, `ADV-Q1`, `SRV-Q1`, `CLT-Q1` (`lanes.toml`); the numbered ids (`Q55`) stay. A new entry goes under its lane's block at the end of the "Open" section, as `#### <CODE>-Q<n> — title` (blocks keep concurrent lanes from editing the same lines).

## Open

### Q2 — Project name and crate prefix

The repo is `homm3`; crates use the provisional prefix `h3-`. "Heroes of Might and Magic" is a trademark of its owner; a public project name should probably avoid implying endorsement. Decide before first public release; renaming later is cheap but not free.

### Q4 — Confirm local compute

Is the CPU a Ryzen 9 3900X (12 cores/24 threads) or the non-X 3900? How much RAM? Used to set initial benchmark and self-play expectations; not blocking.

### Q5 — RL implementation language/framework

Deferred. Options later: Python + PyTorch (ecosystem), Rust-native (burn/candle), or other via C ABI. Decide when E05/E06 are refined. Note the GTX 1070's Pascal architecture may constrain framework/CUDA versions.

### Q7 — Supported platforms for the core

Proposed: native Windows, Linux, macOS and WASM compile targets for the logic crates; CI initially Linux + Windows. Confirm.

### Q10 — Multiplayer model confirmation

Design assumes **authoritative server with per-viewer projections** (`06-security.md`); lockstep with full state is excluded because it leaks hidden info. Confirm this matches intent for any future multiplayer.

### Q22 — Jousting: path length or start-to-end distance (E03 T5)

Wiki (Cavalier page): the bonus is "calculated based on the distance between starting and ending positions". VCMI passes the length of the path actually walked. They differ when obstacles or stacks force a detour. **Implemented: path length (VCMI)** (BAT-DMG-005). **Experiment:** place a Cavalier so that its shortest path to the target detours around an obstacle (e.g. 5 steps for a straight distance of 4); compare its damage on a fixed target with a 4-step straight charge (+25 % vs +20 % of base).

**Not in batch 1a** (2026-10-03): the experiment needs a controlled detour and, because Champion damage is random, many repetitions. If a task needs the answer, reading the game's code is the cheaper last resort (Q29); otherwise VCMI's path length stays.

### Q43 — Chain Lightning: the sprite offset in the jump distance (E04b T2d)

The original picks Chain Lightning's next target by screen distance; the y position of each stack is lifted by half of `267 − the top offset of its creature's sprite frame` (`docs/formats/installation.md` §7.8). The offset comes from the creature's DEF file (`H3sprite.lod`), a graphics value the packs do not hold. **Implemented (user, 2026-10-06):** hex-centre geometry with the two-hex shift and the original's tie order, without the offset (BAT-MAG-006); batch 2a checks the geometry. **Options later:** harvest the offset per creature (stage `H3sprite.lod`, a minimal DEF reader in `h3-harvest`, a creature field), or keep the approximation. Matters only when two candidates are nearly equally far; decide after batch 2a. **Batch 2a** (R1, R2) confirmed the screen geometry and the tie order with stacks of one creature type, where the offset cancels; it says nothing about mixed types. Still the agent's recommendation: keep the approximation until a task needs the sprite data anyway.

### Adventure lane (`ADV-Q<n>`)

#### ADV-Q1 — Cross-context ids `PlayerId` and `HeroId` in `h3-contracts` (E08 T1a)

`h3-adventure` (a hero's owner, fog per player, the actor of its commands), `h3-game` (the players) and later `h3-heroes` (the hero store, ADR-0013 point 1) must name the same player and the same hero, and domain crates cannot import each other. **Options:** (a) both ids in `h3-contracts`, added by T2's `shared/` pull request (a seam addition that no battle code reads); (b) each context keeps its own handles and `h3-game` maps between them in every projection and seam. **Recommendation:** (a) (ADR draft "crate shape", point 5). Blocks T2.

#### ADV-Q2 — How an adventure replay names its map (E08 T1a)

A battle replay carries its setup. An adventure setup holds every tile (41 472 on a two-level SoD map of 144×144) and every object, so embedding it bloats every replay; naming the map file makes a replay depend on the importer. **Options:** (a) the replay names the map by content hash and path (a committed fixture, or the server's copy next to its journal) plus `h3-map`'s import version; verifying re-imports, and an import change bumps the version as a state-hash change does today; (b) the replay embeds the setup in a compact, versioned encoding; (c) the replay embeds the map file's bytes. **Recommendation:** (a); (b) only if saves need it. Shipped maps never enter git either way (ADR-0009). Blocks T9 (and the server's journal at E16 M5), not T2–T8.

### Server lane (`SRV-Q<n>`)

Context, options and recommendations for all of these: `docs/epics/E16-server.md`, "Questions for the user" (the E16 refinement's first draft, 2026-10-08). Blocked until answered: the correction of the drafts and the server `QUEUE.md`.

#### SRV-Q1 — Where the server runs first

Loopback, LAN or internet. Recommendation: loopback and LAN until identity (M3) exists; the internet also needs a reverse proxy for TLS.

#### SRV-Q2 — Authentication now or later

Recommendation: seat tokens only in M1–M2, the keypair identity in M3.

#### SRV-Q3 — Which client connects first

The headless test client, then the client lane's viewer; proposal that the viewer consumes `h3-protocol` messages live or from a record file with the same code.

#### SRV-Q4 — Spectators

Public events only, or a `Viewer::Spectator` in the battle's `observe` (a battle-lane API change) before M2.

#### SRV-Q5 — Runtime and wire format

Std threads and JSON as recommended, or `tokio` and/or a binary format from the start.

#### SRV-Q6 — What `h3-game` must expose for the whole game (M5)

A player actor for `apply`, `observe` for a player and a spectator, pending decisions as state, a trusted system actor for timeouts and disconnects. May the server lane file this as an adventure-lane request (input to E08 T1a, ADR draft 3)?

#### SRV-Q7 — Timing

Start M0 now (the mapping's "other" fallback protects the build from E04b/E04c additions) or wait for E04b's close.

#### SRV-Q8 — Account model

Password-derived keypair (recommended: name and password become a signing key on the device, no secret is sent or stored, any device with the password has the account; two crypto crates, `ed25519-dalek` and `argon2`) or classic password accounts hashed on each server (one crate; the password travels, so every login needs TLS). A keypair per device was dropped: a new device would need the key file (the user, 2026-10-08).

#### SRV-Q9 — Persistence

Journals and JSON-lines logs in a data directory, synced per write and rebuilt at start (recommended), or an embedded store from the start. The write-ahead journal, which restores open games after a crash or a pause by re-running them, is the same under both.

#### SRV-Q10 — Milestone order

Ranked battles (M4) before the whole game (M5), as proposed.

#### SRV-Q11 — Server discovery

A web of trust between servers (recommended: every server has a keypair and signs a card describing itself; operators vouch for peers in the configuration; clients browse the cards relayed by servers they know and see the vouching chain; signed community lists as files; mDNS on the LAN), with resolution by key through a DHT deferred; or a DHT from the start; or no discovery in the core (community lists on a web page). Draft: `docs/lanes/server/adr-drafts/discovery.md`.
