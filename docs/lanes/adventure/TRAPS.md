# Adventure lane — standing traps

Moved out of the lane's HANDOFF on 2026-10-24 so that session start stays short; verbatim, grouped by area. Read the group for the area your task touches; delete a trap when it stops applying, merge duplicates, add a new one under its area (a trap of every lane goes into `docs/HANDOFF.md` or the topic doc it belongs to, a `shared/` change).

- Cheap forks are a hard requirement (decision 6): no per-fork deep copy of map-sized data; pointer identity never in logic or the hash.
- RNG seeds and stream positions are server-only state (decision 9): never in an observation, never seeded from client data.
- Template masks: bit `j` of byte `i` is the tile `7 − j` columns left of and `5 − i` rows above the anchor (`h3m.md` had it mirrored until T5a); check a geometric reading of the format against the shipped maps (towns' gates, heroes' tiles) before building on it.
- Stage archives, not files: the user's `original-data/maps.tar` (the shipped maps; untar into `original-data/install`) and `extracted.tar` (the text tables); the sprite archives for `.msk` sizes. `sandbox-setup.sh --lane adventure` copies only the engine's files (copy the harness's DLLs, sprite LODs and sound archives to `original-data/install`) and skips the client gate's SDL packages; it looks for the unpacked `extracted/H3bitmap/Objects.txt` in the staging folder, so with `extracted.tar` staged alone its baseline runs without the original data (E08 T99b2a): stage `Objects.txt` too, or run the scoped verify `--with-original-data` after untarring into the clone.
- A shallow clone: `git fetch --depth=60 origin master` before `sandbox-setup.sh`, or its baseline runs in full.
- A `CARGO_TARGET_DIR` outside `target/` is not gitignored: keep extra target directories under `target/` (`target/cov`), or `git add -A` commits gigabytes.
- An experiment's map and template must come from the same compile (batch 1a's map predated the review's Q4c, T10c): after any change to a spec, compile again and copy the map to the user's folder in the same step. Since T16b a mismatch shows: the map's description starts with `Stamp <hex>.`, the template's top with its own (`docs/experiments/README.md`).
- An experiment row that reads a path must click explored tiles: the original draws no path onto an unexplored tile (ADV-MOV-008), so a target past the hero's radius (5 without Scouting; ADV-FOG-002) reads "no path" whatever lies there (batch E7's E7-23 corridor, T58). Put the targets within the radius, or have the recipe read `explored:x,y` before the click.
- A batch played past day 7 needs a town for each player (`[[map.town]]`, any owner since E08 T78): the original defeats a player seven days after it holds no town (player +0x3D), so a townless hot-seat run ends at day 8 (batch E9b, T78's review). Count the town's gold in the predictions.
- Price an experiment's walks before staging it (E08 T78): a throwaway test in `h3-map`'s tests reads the written map, imports it, moves the hero in a cloned setup to the leg's start and reads `GameState::new(...).adventure().reach(...)` (`points_left`, `path`). The query covers only the tiles the player has explored at the game's start, so a leg past them shows none: the original's rule too, split it into legs. Keep the test out of the commit.
- A second click on a path whose first step the hero cannot pay today (its mark red beside the hero) keeps the hero where it is and sets its points to 0 (batch E8a's E8-4, E08 T68a's first run): a row that reads a step after such a click needs `once` (`clients/capture/`) or a hero of its own.
- In a hot-seat batch a battle whose two sides are human players' (an owned mine's guards are their owner's side) refuses auto combat: the key leaves it off and each side's stack waits for an order (batch E9a's E9-2, E08 T79a). Plan it `battle = "auto again"` (it falls back to `attack`) or `attack`, never `auto`, which waits until its time limit.
- A shared change the lane needs (Cargo members, `arch.toml`, `lanes.toml`, contracts, kernel, xtask) goes in a `shared/` pull request; one that must land with lane paths (a new crate) needs the user's consent and the label `cross-lane`. A `shared/` or cross-lane branch runs the full verify (its scoped `check-lane` fails by design).
- A field added to a type other lanes build in code (`GameSetup`, `HeroDetails`, `AdventureSetup`): the scoped verify builds none of their test targets, so run `cargo check --workspace --all-targets` before the pull request; and grep for the type's name, not a field's (`banned_skills` is also the experiment writer's `Map` field, E08 T61b).
- The property plans' strategy (`h3-map`'s `play.rs`, `plan()`): a draw appended last keeps the regression files' maps, but every later argument of a case (the profile, the seed, the steps) draws anew, so the fixed-case cover tests (`the_plans_*`) can lose a rare count; raise their cases rather than tune the draw (E08 T64b: `the_plans_meet_and_manage` from 96 to 320). A change of what `lay_out` lays out does the same to every plan it touches (E08 T97b2, the dwellings on water: `the_plans_fly_and_walk_on_water` 64 to 96, `the_plans_play_battles_to_a_victory` 192 to 320).
- The adventure part's content hash is recorded in the AI lane's bots tables (`python/records/bots-report-v1.json` and `bots-neutral-v1.json`, `engine.adventure`), which its pytest compares with the engine's (pytest is not in CI's verify): a change of the part or the original packs' adventure files moves both lines (`cross-lane` with the user's consent; E08 T70, T72). The replays' headers record it too.
- The plans' oracles meet increment 9's objects since E08 T86b1 (`h3-map`'s `play.rs`): a visit's adventure events may be a flag and its reveal, then a Shipyard's refusal (`landing`); a Leave Guards dialog is an army dialog that opens empty, then tells the mine's guards, and whose `Close` keeps the group as the guards, losing nothing (`check_groups`, `check_legal`, the held joins in `check_conservation`, `check_mine_guards`); a battle without a defending hero or a monster is a mine's guards' (`check_mine_battle_end`); `lay_out` leaves out an ownable object entered on water (the import refuses it), since E08 T97b2 but a dwelling or a random dwelling (a hero in a boat visits it, survey `E08-dwellings.md` §17). An oracle that finds an object by its tile uses `visited_at` (the objects added in play first, as the engine's `tile_object`).
- `lay_out` serves the committed fixtures too (`fixtures.rs`): whatever a new draw adds must leave a plan without it byte-identical (E08 T75b: boats are laid out after every other object and the coast is marked only on a map with boats). A resource the plans' properties see given is counted once: a removed object's contents by `check_conservation`'s removal path, a chest's and a find's (leaving or emptied) by `visit_gains`.
- A generated map's or test's "blocker" of an arbitrary class becomes a typed object once its class gets a kind (E08 T72: 124 became the hole): the generators use 118 (a crater); the class tables are in `h3-map`'s `import/codes.rs`.
- Objects added in play (E08 T83b2a, T85a: a creature month's monsters) come after the static map's in map order: read an object by a found index through `AdventureState::object_at` (or `object`), never `map().objects()[index]`, and make a lookup by tile or by type and anchor walk the added objects too (T85a's audit: `object_named` missed them, so an added monster's offers never stood). A read left on the static map says why in its doc. The plans' oracles too (`h3-map`'s `play.rs`, `view.rs`): since T85b their games reach a creature month, so a found index (a guard's, a visit's) may be an added monster's (T85b1: a guard read through `map().objects()[i]` panicked past the static list).
- A new read in the reach's or the passage's loops costs on every map where its block exists: the occupancy exists on most played maps (any removal), so a test hung on it is paid everywhere (E08 T83b2a's first cut: +9 to +16 %). Give new state its own `Option` block, serve it in the walking search's rare case (`AFLOAT`; a third instantiation changed the compiler's inlining of the plain loop) and a `#[cold]` slow path; compare `callgrind_annotate --inclusive=no` with `master`'s, measured by `cargo xtask bench-check --workload <name>` in a `git worktree` under `target/`. E09 T8a2: any edit inside the walking search's marking loop or its occupied branch moved the loop's code by +1 to +8 % (`reach-xl-144`), untouched callees such as `walking_step` included; a new per-tile fact goes through a `#[cold]` pass before the loop (`Reach::unmark_visitors`) and a callee kept out of line (`visit_at`, `#[inline(never)]`); even sharing `tile_object`'s lookup with a new helper (`tile_index`) moved it out of line and cost +2.0 to +2.8 % (`reach-lifted-xl-144`, `random-play-duel-36`), so the helper keeps its own copy.
- A workload's `collect` pattern counts inside every symbol that matches it: name the counted function so that no other symbol holds its name (E08 T86b2: the counted `day_start_step`, its run-up `play_to_day_start`; a first `*day_start*` would have counted the whole run-up). A new workload's file starts with `instructions = 1` and `cargo xtask bench-check --update --workload <name>` writes its count. A small workload whose count is largely glibc's malloc follows the heap's earlier state, which differs between the sandbox and CI's runner (T86b2's `day-start-xl-144`: +2.7 % on CI with a fork alive during the counted step): drop what the run-up allocated for the step before it, so the step reuses the same freed chunks; test with a longer `--root` under `valgrind --tool=callgrind --toggle-collect=<pattern>`.

- Counting increment 10's events (E08 T96a): a purchase's joins are `CreaturesJoined`, as the free creatures' are; tell them apart by the answer before (the hire question's accept, or a `Buy`). A refusal cannot stand in a golden replay: `Replay::record_commands` stops at the first command the game rejects, so a script shows a refusal as the legal set without that `Buy` and checks the error on a copy in its probe.
- The capture harness's hire dialog (E08 T90): the topmost dialog's vtable is 0x640C4C, not the manager's 0x640C70 that `docs/exe/map.toml` names; the manager (the most +0xAC, the amount +0xB8) is 0x80 after the dialog, else found by a scan (`h3mem.recruit_manager`). A settle that does not know a screen returns with it open and the next step's key fails.
- A computer player's turn is not shown as the current player (E08 T90, batch E10a's Tan): `end_turn` polled Blue then Red, Tan never; read the computer's own state (`treasury:tan`, its hero) before and after instead of `ai_turns`.
- The harness check's battle `attack` plan (a strike by the cursor's frame) failed once in two runs with the changes of E08 T90, which touch no battle code (`no attack cursor over hexes`, every frame 6), and passed on the rerun: run it twice before blaming a change.
- A row's two branches as `only_if = { at = [x, y] }` steps (the capture harness, E08 T100a): the first branch played can leave the hero on the other's tile, which then plays too (batch E11a's E11-8 in its first run: Uf to Un, then Un back to Uf and a jump): put first the branch whose end cannot be the other's start.
- Replay Opponent Turn's view (E08 T100a): the view's corner in memory moves to a jump's exit while the screen still fades the old view out and never draws the exit's; read what Red saw from the frozen clock's dumps (`dumps = "every"`), not from `replay:views`, and never from a real-time dump (it lags a view).

- **Procedures as skills:** for a speed or replay question use the skills `homm3-bench-regression` and `homm3-rerecord-replays`; measure right after the first build (`AGENTS.md`, "Measure before you polish").
