## Findings

### R4-1 [bug] The hover facts apply their class rules to the map file's class, the hint reads the game's: a shipped abandoned mine (220.7) gets no `mines` row, a vertical garrison (219) is never `armed`
Where: `src/engine/hover.rs:164-233` (`table`: `match class { MONSTER, TOWN_CLASS, GARRISON }`,
`contents.add`'s `class == MINE`), fed by `src/engine.rs:298-311` (`drawn` = the template's own
class) and `:333-343`. What: `sight.classes` holds the class as the map file gives it; the
mouse-over dispatches on the tile record's class *as the game loads it* (`Records::game_class`,
`[map.records] loaded_as`, `map/assets/base.toml:369-370`: `[219, 33]`, `[220, 53]`). So for an
object of class 220 (`h3_map/src/import/codes.rs:95-97`: "every shipped one is 220.7, the
abandoned mine"; Objects.txt's `AVXam*.def`) the engine's start writes no `mines` row, and
`hover.rs:904` (`(53, Some(Content::Mine { .. }))`) falls to `_ => Hint::Object(53)`: the bar
shows the class's name without the abandoned mine's name and guards, where the capture (and the
original) writes a mine row by the game's class (`capture/h3mem.py:2178-2180`, `if cls == 53`).
For class 219 `GARRISON => ...` never matches, so `armed` is 0 for every vertical garrison
(`hover.rs:1117-1119` tests `GARRISON` on the game's class); latent today because the cursor
returns before that test without `reach` (MCL-Q37) and another team's garrison at level 0 holds
none. Evidence it is not caught: the comparisons' abandoned mine is `AVXabnd0.def`, class 53.7
(`engine-start-owners.toml:27`; the tests' `hv537.def`, `tests/engine.rs:903`), and T3b2's two
shipped starts were chosen with no abandoned mine in sight. It shows on the 8 shipped maps the
engine plays whole and on their golden replays. Suggested fix: map `drawn`'s class through
`Records::game_class` before `hover::table`'s class rules (`engine::start` takes
`&tables.records` or a `Records`), or key them on the engine's `ObjectKind` (`Mine`, `Garrison`);
add a 220.7 and a 219.0 object to `tests/engine.rs`' `HOVER`. Effort: S.

### R4-2 [bug] `render --check` without `--record` reports a passing check
Where: `src/bin/h3-map-view/render.rs:182-186` (`run`), `:226` (`render`), `:71-160`
(`Options::parse`). What: `--check` is taken alone; without `--record` `render` draws and writes
the PNG and returns `Ok(out)`, and `run`'s `Ok(path) if options.check` prints "render: <out.png>:
its start is the capture's" and exits 0. A forgotten `--record` (or a script that drops it)
turns the comparison into a pass that compared nothing. Suggested fix: `parse` refuses `--check`
without `--record` and `--live` (and `--packs` without `--record`); a parse test. Effort: S.

### R4-3 [bug] `render --record` builds the engine's start on the art `--live` already changed: a random dwelling's comparison is vacuous, and `h3map.py engine`'s pixels inherit the capture's drawn objects
Where: `render.rs:221-236` (`read_live(.., &mut art, ..)` first, then `record_start(.., &art,
..)`), `apply_live` `:604-628` (a random dwelling the capture resolved: `art.templates.push`,
`art.objects[index].template = ..`), `engine.rs:298` (`objects::template(art, index)`). What:
after `--live`, a random dwelling's template in `art` is the capture's dwelling, so
`engine::start` writes the capture's DEF and class for it and `engine::differences` cannot
report MCL-STUB-1 there (a random artifact's is reported: its template is not replaced). The PNG
`h3map.py engine` counts (`run(*common, ...)`, `h3map.py:2056`: `--live kept --record`) is the
engine's start drawn over the capture: a key the start does not write stays the original's, and
so does a random artifact's `drawn` (the engine's DEF equals the template's, `same` at `:597`, so
it is not reset). The record-only path (`paint::played`, `Painter::new`'s `None` arm) builds a
fresh art, so the window draws what the check never compared. No current engine situation holds
a random object (checked: `engine-start-*.toml`, `start-jared`, `start-good-witch`), so no
recorded result is wrong today. Suggested fix: pass the file's art (`MapArt::from_raw(&raw)`
before `read_live`) to `record_start`; for the PNG either reset the seen objects' `drawn` before
the engine's table or say in `run_engine`'s docstring that the pixels measure what the start
writes only. Effort: S.

### R4-4 [risk] A record its bound cut (header `first` > 1, opening on a later `GameSnapshot`) is shown as a new game's start
Where: `engine.rs:167-184` (`parse` never reads `header.first`), `:241-246` (`first`). What: a
whole game's record keeps "the newest that may begin the record and those after it"
(`h3-protocol/src/session.rs:316-330`; `GameRecordHeader::first`, `manifest.rs:107-109`: "higher
once its bound let the oldest go"); a server's records are bounded at 512 KiB by default
(`h3-server/src/config.rs:638`), only `h3-server record` passes `usize::MAX` (`record.rs:114`).
Such a record's start is a mid-game snapshot, and the start's new-game rules then misfire: every
hero faces right, the hero list is sorted by type (hires not appended), an object added in play
refuses the record (`Refused::Object`), and a town that built a Fort since refuses it in
`apply_live`'s town check (`render.rs:586-595`) with "object i: the original drew the town as
<the engine's picture>, its buildings give <the map's>" (the message names "the original" for the
engine's table: wrong either way). Not on the review list. Suggested fix: `Refused::Cut(first)`
for `first != 1` until T4 folds from a mid-game snapshot (or state the case in the module doc
and the design); reword the town check's message for a record's table. Effort: S.

### R4-5 [contract] The date's month and week are computed in the client
Where: `src/engine/panels.rs:123-133`. What: the month `(day-1) / (week_days*month_weeks) + 1`
and the week of the month are the client's arithmetic; the engine's `CalendarParams` gives only
`weekday` (`h3-adventure/src/ruleset.rs:269-278`), its month length lives in
`h3-game/src/state/day.rs:97`, and the observation carries `day` alone. Small, but it is the
"rule copied into the client" the user forbade at T3b's start, and T3b1's review item does not
list it (it lists morale, luck and the movable flag). Suggested fix: an `MCL-Q<n>` and an
adventure-lane inbox note (a `CalendarParams::month`/`week_of_month`, or the numbers in the
view); meanwhile name the copy in the review list. Effort: S.

### R4-6 [risk] `--check` passes silently where the capture has no `[hover]` or `[chosen]`
Where: `render.rs:368-400` (`hover_differences`: "nothing when either has no facts", `let (Some(a),
Some(b)) = .. else { return Ok(Vec::new()) }`), `engine/panels.rs:401-403`. What: a kept live part
captured before T3b2 (no `[hover]`) or without `[chosen]` makes those comparisons no-ops while
`run` still prints "its start is the capture's". All six engine starts are recaptured today, so
this only bites a stale or hand-made capture. Suggested fix: push "the capture has no `[hover]`:
the mouse-over not compared" into `found` (or print it beside the pass). Effort: S.

### R4-8 [doc] `main.rs`'s usage of `render` names no `--record`, `--packs` or `--check`

options exist only in `Options::parse`'s doc comment (`render.rs:66-70`), so `h3-map-view` without

`--check` (compare with `--live`'s, draw nothing). Effort: S.

### R4-10 [simplify] A record is decoded twice per load
Where: `render.rs:427` (`engine::parse(&text)?.header`) then `:431` (`engine::load(&text, ..)`,
which parses again at `engine.rs:219`). What: a golden replay's record (every snapshot, event
and reveal of a whole game) is JSON-decoded twice per `render`, `record`, `window --record` and
`sequences --record` start, and `paint::played` reads the map file a second time
(`paint.rs:147` after `:380`). Suggested fix: `engine::load` takes a parsed `GameRecord` (or
`load_record` reads the header line alone). Effort: S.

### R4-11 [nit] `engine::start` can index past `loaded.raw` with an art of another map
Where: `engine.rs:280` (`count` from `art`), `:314-319` (`owners` from `loaded.raw`), `:332`
(`owners[index] = ..`). What: the test treats another map's art as `Refused::Setup`
(`tests/engine.rs:444-456`), but only the static objects' count is checked; an art with more
objects whose extra ones shift a kept index past `raw.objects.len()` panics. The binary always
passes the record's own art, so no input file reaches it. Suggested fix: refuse `Setup` when
`art.objects.len() != loaded.raw.objects.len()`. Effort: S.
