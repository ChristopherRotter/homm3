## Findings

### F-r4-1: Several turret clauses with gameplay effect have no test
- rules: BAT-SIE-016, BAT-SIE-018, BAT-SIE-019
- kind: test-gap
- severity: low
- confidence: high (grep of `tests/turrets.rs`, `properties.rs`, `sieges.rs`, `walls.rs`, `aim.rs` for the clauses)
- evidence: (a) "the turrets, then the Catapult" (`turn.rs:62-63`): every turret test runs without an attacker's hero, so no Catapult is ever on the field with a turret; `grep -rni "then the catapult|before the catapult"` in the tests finds nothing (`sieges.rs` tests the Catapult first without turrets). (b) A waited turret acts first in the wait phase (`turn.rs:45-67`, the original 0x464F50 tests "is 149" before the phase's speed order; batch AT1): `turrets.rs:231-234` only asserts that after `Wait` the next stack is 2 (the normal phase), the comment "it then acts first in the wait phase" is not asserted. (c) The battle's end with turrets alive and the defender's army dead (the attacker wins, `check_end`'s `WAR_MACHINE` test): `turrets.rs:458-480` only tests the converse (the attacker dead, the defender wins); the `siege-s7` replay may cover it but pins nothing by name. (d) A turret's shot that kills the last attacker stack ends the battle, and the rebirth after it (`turret_shot` lines 471-472). (e) Armorer of the *controller's* hero for a hypnotized target (`turret_inputs` line 436; the original 0x443DE6): untested. (f) Magic Mirror never redirects to a turret (`magic.rs:1103-1109`): untested with a turret present.
- fix or test sketch: in `turrets.rs`: (a) `at(.., Castle, [Some(hero), None], ..)` → the start's events: strikes of 2,3,4 then the Catapult's `WallShot`/wall event, in that order; (b) with `gunner` as the defender's hero: `Wait` the keep, let every other stack `Defend`, then assert `s.active() == keep` while another stack (a slower defender's one) also waited and would otherwise go first; (c) set the defender's army stack count 0, `check_end`, assert `Victory(Attacker)` and the turrets still alive; (e) set `HYPNOTIZED` on stack 0 with the defender's hero having Armorer 15 %: the keep's shot must be `sum * 85 / 100`; (f) a mirror chance 100 on an attacker's stack, the attacker's hero casts a negative spell at a defender's stack: the `SpellRedirected.to` is never a turret over many seeds.

### F-r4-2: "A turret can always shoot" is not implemented: the commanded turret's Shoot needs `shots > 0`
- rules: BAT-SIE-018 (summary: "A turret can always shoot (no shots needed, never blocked; the original's 0x4428F0)"), BAT-SIE-016 (Artillery commands it)
- kind: rule-text (code) / robustness of the data path
- severity: low (only a pack whose turret creature has `shots = 0` and no `unlimited_shots` shows it; the harvested Arrow Tower has 99 and the engine never spends them)
- confidence: high
- evidence: `war.rs:57` `is_commanded` = `commanded_ballista(..).is_some() && can_shoot(..)`; `command.rs:298` the Shoot command needs `can_shoot`; `combat.rs:53-66` `can_shoot` = SHOOTER ∧ ¬NO_SHOOTING ∧ (`shots > 0` ∨ UNLIMITED_SHOTS) ∧ (WAR_MACHINE ∨ …). The automatic path (`war.rs:108-113`) shoots without that test, and `aim.rs:148` treats a turret as "shoots" unconditionally. So with a turret of 0 shots: without Artillery it shoots every round, with Artillery the keep is activated as automatic (`is_commanded` false) and also shoots; but if a client builds such a creature with `shots = 0` *and* a commanded path (e.g. a future pack change), the Shoot command is refused with `CannotShoot` while the rule promises it always shoots. The original (0x4428F0, per §7.30, not re-read by me) lets creature 149 shoot with no shot test.
- fix or test sketch: in `can_shoot` (or `is_commanded` and the Shoot plan) treat `is_turret()` as the Ballista's "war machine" short-cut *and* skip `has_ammunition` for it (`s.is_turret() || (has_ammunition(s) && …)`), or let the pack compiler require `shots > 0` or `unlimited_shots` for a `turret` creature and say so in the summary. Test: `turret_ruleset` with the TURRET's `shots=0` → with `gunner` the legal commands still list Shoot.

### F-r4-3: BAT-SIE-019's "immune to every spell" is enforced in code for every path but Sacrifice's victim, which rests on the pack's `excludes = ["war_machine"]`
- rules: BAT-SIE-019
- kind: rule-text / test-gap (a data-dependent hole; no behaviour bug with the shipped packs)
- severity: low
- confidence: high (traced); medium on what the original does (0x5A8090's Sacrifice victim case 0x5A8523 was not re-read for creature 149; the turret is unclickable there anyway)
- evidence: `magic.rs:1264-1267` → `raise::victim` (`raise.rs:265-280`) tests alive, own side, controller, not created, `affects(ruleset, spell, creature, guard)`; it never calls `affects_stack` (the only place with `!stack.is_turret()`, `magic.rs:835`). `affects` (`magic.rs:770-805`) has no turret or war-machine test of its own; the exclusion comes from `conditions.admits` with the spell's `excludes`: `packs/base/battle.toml:1468-1475` (`sacrifice`: `excludes = ["undead", "war_machine"]`), `packs/synthetic/battle.toml:654-662` (`offer`, the same). A pack without that exclusion would let the defender's hero sacrifice its keep (5 × 100 hit points) to raise its army — the turret is "immune to every spell" in the rule but not in this path. The test at `turrets.rs:427-440` checks `affects_stack` only.
- fix or test sketch: add `&& !stack.is_turret()` to `raise::victim` (one line, keeps the rule's guarantee off the data), and a test: a `turret_ruleset` whose Sacrifice has no `war_machine` exclusion → `Command::Cast { spell: sacrifice, target: own stack, second: the keep }` is refused.
