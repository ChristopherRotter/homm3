## Findings

### F-r3b-1: A Cyclops may shoot the gate while a living stack stands in it; the original offers no such shot
- rules: BAT-SIE-013 (BAT-SIE-014's command path)
- kind: behaviour-bug
- severity: medium (a stack standing on the open gate's hex; the Catapult is not affected)
- confidence: high on the reading; medium on how often the setup arises in play
- evidence: battle_cursor 0x47668C–0x4766B9: the hovered hex's record byte +0x18 (the living stack on it, 0xFF when none; `structs.toml` 207, 0x468730) is tested, and the wall-shot branch 0x47684B is taken only when it is negative (no stack) **or** the acting creature is 145 (the Catapult). For any other creature (the Cyclops) a hex holding a living stack goes to the stack-target path (an attack or a shot at that stack). The gate's aim hex is its own hex 96 (0x63BE60 record 3; the engine's `targets[3].wall = 96`), and a living stack may stand there while the gate is open (`close_gate`, `siege.rs` 546–563 keeps it open for exactly that). The engine's `commanded_wall_shots` (`siege.rs` 750–766) and the `ShootWall` plan (`command.rs` 313–325) test only `stands(part)`, so `legal_commands` lists `ShootWall { part: 3 }` and `apply` fires the shot. Scenario: Fort, a defender stack stands on hex 96 (gate open), the attacker's Cyclops acts → original: the click on 96 offers the shot at the stack (or an attack), no wall shot at the gate exists this turn; engine: `ShootWall { part: 3 }` is legal and hits the gate. The other targets are unaffected: the walls' aim hexes are wall hexes nobody stands on (62 stays blocked for good), the towers' and keep's are off the field.
- fix or test sketch: in `commanded_wall_shots`/the plan, for a shooter that is not the Catapult, refuse (and do not list) a target whose aim hex holds a living stack; with the current field only the gate qualifies: `kind == Gate && living stack on s.gate` (a corpse does not count: +0x18 is the living stack). Test (`walls.rs`, `needs-run`): Fort, `("cyclops", 5, 3, 5)` against `("fixed", 5, 13, 5)`; open the gate and `place` the defender's stack on the gate hex; `activate(0)`; `assert_eq!(wall_shots(&legal(&s, &r)), [1, 2, 4, 5])` and `act(ShootWall { part: 3 })` is an `Err`; the same with the Catapult commanded (Ballistics) still lists 3.

### F-r3b-2: The catalog states the tie-break's direction backwards (or ambiguously); no test pins it
- rules: BAT-SIE-014
- kind: rule-text (and a low test-gap)
- severity: low
- confidence: high
- evidence: catalog summary: "a tie decided by random(1, 100) at most 50 **for the first**". The code 0x445F5C–0x445F7A (and the re-aim's 0x445E34–0x445E52): on an equal distance the roll `random(1, 100)`, and `≤ 50` **replaces** the candidate held so far with the later one in the list's order (`> 50` keeps the earlier). `installation.md` §7.29 says it right ("a tie replaced with random(1, 100) ≤ 50"), and `siege.rs` `nearest` 782 implements the replacing direction. The test `a_missed_shot_lands_on_the_nearest_other_wall` only checks that both tied walls occur (`landed(all, 3) == [Some(2), Some(4)]`), not which roll picks which; the direction matters only for replaying the original's draws, not for the engine's own determinism.
- fix or test sketch: reword the summary ("a tie replaced by the later wall of the list when random(1, 100) ≤ 50"). Optionally a test on `nearest` with a stubbed roll sequence, if the test support can seed a known first roll.
