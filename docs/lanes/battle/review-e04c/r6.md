## Findings

### F-r6-1: BAT-QUIRK-23's class: the evidence points to `preserve` (or no quirk), not `fix-optional`
- rules: BAT-QUIRK-23, BAT-SIE-029
- kind: question
- severity: low (the ledger's class; only retiring the flag would change play, in strict-fixed)
- confidence: medium; a wiki check (below) would settle the community status
- evidence: the original's skip is a deliberate branch, not an accident: 0x4637B6-0x4637C3 tests
  the fort level and `side == 1` explicitly before setting the Ballista up. VCMI's comment
  (`lib/battle/BattleInfo.cpp:326`, "defending hero shouldn't receive ballista (bug #551)") calls
  the *opposite* behaviour (a defender's Ballista) its own bug, i.e. the reimplementation treats
  "no Ballista for a town's defender" as the game's rule. The ledger entry
  (`quirks-ledger.md:473`) says "Community status: unknown (not searched)" and in the same line
  quotes this. `docs/04-rules-and-sources.md` §4 step 2: a behaviour the community treats as the
  game's known behaviour is `preserve`; `fix-optional` is for "unintended" ones. The user decided
  `fix-optional` (BAT-Q48); this asks only whether the user saw that VCMI's "bug #551" is evidence
  for intent.
- fix: put the question to the user with the VCMI reading spelled out. Reclassing to `preserve`
  changes no profile default (faithful turns on both classes, strict-fixed fixes every quirk), so
  it is a ledger correction; the alternative with an effect is to retire the flag as the
  original's rule (as BAT-QUIRK-1 was), which removes the strict-fixed variant.

### F-r6-2: The defender's `may_retreat` at a town tells the attacker whether the town has an Escape Tunnel
- rules: BAT-SIE-024 (ADR-0013 point 9)
- kind: security
- severity: low (one bit of hidden town state; it decides whether the attacker can expect to destroy the defending hero)
- confidence: medium; depends on the town's buildings being hidden from the attacker (the town context, E09, is not refined)
- evidence: `observe.rs:195` publishes `may_retreat` for both sides to every viewer; at a town the
  defender's value is `Siege.escape_tunnel` (`siege.rs:408-412`), a building the attacker cannot
  see. ADR-0013 point 9 makes the retreat options public because "the original shows" them, but the
  original enables the buttons for the acting side only (0x478573 reads +0x132C0): the attacker
  never sees the defender's Retreat button. Before E04c the option depended only on public facts
  (heroes, a worn NoRetreat artifact); the tunnel is the first private input. Scenario: the
  attacker's agent reads `observation.may_retreat[1] == true` at a Stronghold → the tunnel is
  built. (`Observation.siege` also carries the whole `SiegeState`, `escape_tunnel` included, as a
  private field: not readable outside the crate, but in any `Debug` output.)
- fix: project `may_retreat[defender]` (and `surrender_possible`, which is already false) to the
  defender's own observation at a town, or record a decision that a town's buildings are public.

### F-r6-3: BAT-SIE-028 records no VCMI source, but VCMI agrees with the gate passage and contradicts the summon opening the gate
- rules: BAT-SIE-028 (survey row "Teleport, summoning, spell cost in sieges", `vcmi` column)
- kind: source
- severity: low (the defender's summon reaches the gate only when columns 12-15 are full)
- confidence: high for what VCMI does; the original's side rests on the reading alone (my re-read agrees with it)
- evidence: the entry cites only the code reading; the survey row lists `vcmi` as silent on it.
  VCMI 1.7.5: a summon is placed through `CBattleInfoCallback::getAvailableHex` →
  `AccessibilityInfo::accessible(.., side)` (`CBattleInfoCallback.cpp:1640-1645`), where a GATE hex
  is accessible to the DEFENDER side (`AccessibilityInfo.cpp:31-33`): agrees with "placed as a
  stack of the caster's side". But VCMI opens the gate only in a move
  (`BattleActionProcessor.cpp:839-844`, also 887-903, 1005); after an action a closed gate with a
  stack on 96 stays CLOSED (or BLOCKED with one on 94) (`BattleProcessor.cpp:228-262`). So
  "a summoned stack the defender places on 94-96 opens the gate (GateOpened)" is contradicted by
  VCMI. Gameplay effect: while the elemental stands on 96 the gate is open in the original (and the
  engine), so shots and below-Expert Teleport lines across hex 96 pass (BAT-SIE-008, BAT-SIE-026).
  `docs/04` ("Consensus before trust"): a contradiction is a conflict for the user, not settled by
  the reading.
- fix: add a `vcmi` source to BAT-SIE-028 stating both halves, note it in the survey, and queue an
  experiment row (the defender's Fire Elemental summoned onto the gate with columns 12-15 filled;
  read +0x53A4) or tell the user.

### F-r6-4: BAT-SIE-026 and BAT-SIE-025: clauses and batch numbers no test pins
- rules: BAT-SIE-026, BAT-SIE-025
- kind: test-gap
- severity: low
- confidence: high (read every test in town.rs, the relevant ones in sieges.rs, war.rs, properties.rs)
- evidence:
  1. "the line ... may meet no standing wall and not the closed gate, outside the walls too": the
     original runs the line test for every move below Expert (0x5A3760-0x5A37AF, no side test),
     where VCMI tests only moves across the walls (D-20). No batch row shows a move that does not
     cross the walls, and `below_expert_teleport_follows_the_shot_s_line_through_the_walls`
     (town.rs:259) only moves outside → inside. Scenario: a Fort, the defender's stack at (11, 4)
     (hex 79, inside), Advanced Teleport to (11, 6) (113, inside): the line passes the closed gate
     96 → refused; accepted with the gate open or at Expert. Only a test guards this against a
     "VCMI-like" refactor.
  2. TV1's "landing without the moat's damage" (a damaging moat, Advanced Teleport onto hex 61:
     hit points unchanged, no event of damage): `magic::teleport` (magic.rs:2637) calls no moat
     code, but no test pins it.
  3. Neither test reproduces the batch rows' numbers: TB/TV/TE moved from hex 86 to 64, 61, 91;
     town.rs:223 uses (2, 5) to (8, 5), (9, 4), (13, 5), (14, 2). CM2 (three alignments −1, town
     +2 → +1) and RL1 (luck +2) are not run with those values (town.rs:157 uses 1, 3, 9).
- test sketch: in town.rs, `teleport_reaches` with the stack at (1, 5) (hex 86) and cells
  hex 64 (13, 3), 61 (10, 3), 91 (6, 5) at air 1/2/3 → [F,F,T], [F,T,T], [T,T,T]; a defender's
  cast from (11, 4) to (11, 6) at 2 → refused, at 3 or with `gate_open` → accepted; Advanced
  Teleport onto (10, 3) of a `Moat::Damaging` Citadel → `top_hp` and `count` unchanged and no
  damage event; `start(2, 0)` with three alignments → +1.
