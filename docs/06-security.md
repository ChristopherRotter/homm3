# 06 — Security and anti-cheat design

## Scope

The original game had exploits such as spending another player's resources in your town, and in networked play the client held far more information than the player should see. The engine must make that class of bug structurally hard.

Protections apply to the **authoritative (server) mode**: a trusted engine instance with untrusted clients. In local single-player or hotseat with an embedded engine, the local user is trusted (hotseat hiding is a UI concern). The design works in both because the same API is used.

## Trust boundaries

```
untrusted client ──bytes──▶ [transport/decoder adapter] ──typed Command──▶ [session: authenticates → Actor] ──▶ game.apply(actor, command)
untrusted files  ──bytes──▶ [formats adapter: validates, bounds, converts] ──▶ domain types
                                                              game state ──▶ [observe/project per viewer] ──▶ client
```

1. **Identity comes from the session, never from the payload.** The `Actor` passed to `apply` is created by the trusted session layer from the authenticated connection. Commands never contain "who I am" or "whose resources to use".
2. **Commands carry intent only.** No prices, resource amounts, ownership claims, derived stats or results. Everything derivable is computed from state. Example: `TownCommand::Build { town, building }` (E09 increment 2) — cost and payer come from the ruleset and the actor's own treasury.
3. **Validation is total and centralized.** `apply` checks: it is the actor's turn/phase, the actor owns every referenced entity (or the interaction is explicitly modelled), all references exist, preconditions hold, resource checks use the *actor's* stock, bounds hold. The validator runs before any mutation; on failure state is unchanged (atomicity is property-tested).
4. **No reach-through.** Domain functions receive the minimal capability they need (e.g., the actor's own treasury handle), not the whole state plus an id, which makes cross-player access impossible to express by accident.
5. **Legal-command consistency.** `legal_commands` and `apply` share one precondition implementation (or are tested equivalent), so UI hints can't diverge from enforcement.

## Information hiding

- The server never sends full state to a client. It sends `Observation`s and events **projected per viewer**: every event has a visibility scope; `project(event, viewer)` drops or redacts what the viewer may not know.
- Fog of war, unexplored tiles, opponents' unseen armies/heroes/resources, hidden object contents, and opponents' private decisions are excluded from projections. Define per context what each viewer may know (adventure context epic owns the list).
- **Lockstep-with-full-state multiplayer is excluded** by design: every client would hold the complete state and could read everything.
- **Clients therefore need a view model** that applies projected events to partial state. Keeping client code out of the core (ADR-0005) makes this a client concern, but projections are a core contract.
- **Side channels to consider:** RNG seed/stream state must not reach clients (it predicts rolls); saves and replays are exported *per viewer* (redacted) unless the requester is authorized (e.g., post-game); state hashes must not be computed over, or exposed in a form that leaks, hidden data; error messages must not reveal hidden facts ("no such hidden object at tile X" vs. "invalid").
- **Hotseat** hiding is UI-level and out of scope for the core.

### What a viewer may know: a battle (E04a–E04c)

ADR-0013 point 9 owns the list (ADR-0014 for magic, ADR-0023 for a town); `h3_battle::observe` and `project` implement it, the battle's hygiene properties and `h3-protocol`'s frame tests check it. Two points E04c's review settled (the user, BAT-Q50):

- **A town's Escape Tunnel** is its defender's: at a town the attacker and a spectator see the defender's `may_retreat` as `false` and the observed siege without the tunnel (E04c T10b). The original enables the retreat control for the acting side only (0x478573), and a town's buildings are no public fact, but for those that change morale and luck (ADR-0023 point 2, CLT-Q40).
- **The computer's choices for a side** (the automatic turrets' and Ballista's targets, ADR-0023 point 7) read the other side's private Armorer reduction and Artillery level, as the original's computer does, and the target shot is public, so a side may infer something of them from it. Kept as the original in every profile (BAT-SIE-020, BAT-WAR-008; the quirks ledger, beside BAT-Q31's berserk walk, which reads the hidden pits of its own side the same way).

### What a viewer may know: the adventure map (E08)

The list the adventure epic owns (ADR-0016 points 5 and 6, ADR-0017 point 5); `h3_game::observe` and `project` implement it (E08 T8b1), the property tests of E08 T8b2 check it. A player viewer:

- **Public facts:** the map's size and levels, the day, the turn group whose turn is running and which of its players still act, each player's colour; the ruleset (its profile included).
- **Its own:** its explored tiles and their fringe (the hidden tiles touching an explored one, ADV-FOG-005), and its heroes in full: tile, army and its formation, movement points left, and their details (experience, primary and secondary skills, artifacts, spells, spell points; GAM-HER-001, E08 T18b).
- **Explored tiles** show their current content (ADV-FOG-004): terrain, road, river, what objects cover there (blocked and visitable tiles), and the heroes standing there.
- **The fringe** shows terrain, roads and rivers. Under `ADV-QUIRK-1` (the `faithful` profile) it also shows what objects cover there and the heroes standing there: an object's appearance is public there while its contents stay hidden (increment 1's objects have none; contents come with increment 2's objects). A wandering monster shows on the fringe in either profile (E08 decision 40): it guards the explored tiles beside it, so the viewer's legal moves (the reachable tiles, the points left) would reveal it anyway.
- **Another player's hero**, where the viewer sees its tile: its tile, owner, identity and hero type (and so its class, as the original's portrait; E08 T18b), never its army, movement points or details (ADV-FOG-006; what the original's right-click view shows comes with the battle seam).
- **Events:** a hero's step is told to its owner and to the players who see the hero on the tile it leaves or enters, so the viewer learns of a move only where it can see it; a viewer that sees the hero on one of the two tiles is told that tile only. A projected event names the viewer alone, since the full set of its viewers would tell which tiles other players explored. A move is refused onto an unexplored tile before anything else about that tile is checked (ADV-MOV-008), so a rejection says nothing about a hidden tile.
- **Never:** any other tile, other players' explored tiles, the master seed, the streams, the state hash. A viewer that is not a player of the game sees the public facts and no tile.

Increment 2 (objects, the treasury, offers; ADR-0016 points 4–6, ADR-0017 points 1, 6 and 10; survey `rules/surveys/E08-objects.md` §8) adds:

- **Typed objects** are seen whole (type, anchor, masks) once any tile they cover is explored, or on the fringe under `ADV-QUIRK-1` (E08 T12b). The type is public, a random resource's drawn resource included (its picture shows it). Never their contents: a pile's or campfire's amount, a campfire's resource. Objects are listed in map order, never by index: an index counts the objects before it, seen or not.
- **Its own:** its treasury (E08 T13; other players' treasuries are hidden: the Thieves' Guild comes with towns); its per-object state, the Cartographer kinds bought and the keys held (T14, T15); its open decision, kind and price (T14).
- **Events:** a pickup tells its owner the gain (the treasury's change); an object leaving the map is told to every player who sees it there, as the observation shows it (T13). A reveal tells the visitor its new explored tiles only (T14, T15). A border guard's removal and a hero on a border gate are public where the tiles are seen (T15). An offer's opening or refusal (the price not payable), its answer and the price paid are told to its owner only, and a Cartographer's reveal tells it how many tiles it explored; a visit to a kind already bought tells nothing (T14).

Increment 3 (battles on the map; ADR-0013 point 9, ADR-0016 point 6, ADR-0017 points 5, 6 and 11; survey `rules/surveys/E08-battles.md` §9) adds:

- **A battle** (E08 T19a): each of its owners sees its side's observation of it (`h3_battle::observe`: never the other side's private part) and its events by their visibility (a public one to both owners, a side's to that side's owner); its start (the heroes, the tile) and its end (the result) are told to its owners only. Other players learn nothing of it but its effects where they see the tiles (a hero leaving the map). Its seed and stream are server-only as every stream (drawn from the attacking player's stream); under `ADV-QUIRK-5` (`faithful`) its obstacles follow from its tile, as the original's, so they are public in effect.
- **A wandering monster** (E08 T20a2a, T20b; survey §9): its creature and the word of its count (few, several, pack, lots, horde, throng, swarm, zounds, legion) are public where its tiles are seen; its exact count, aggression, whether it never flees or grows, and its treasure are hidden from every player. Its offers (to join, for a price, to flee) are its visitor's owner's decisions, told to it alone with their price (which, with the creature's cost, tells the count); a group joining is told to its owner, its treasure's resources to that treasury; the monster's leaving is public where its tiles are seen. A battle against it is its visitor's owner's (its unowned side's events reach no player); the split into stacks shows in that battle only, and under `ADV-QUIRK-6` (`faithful`) it follows from the tile and the armies, as the original's, so it is public in effect; else its draws come from the attacking player's stream. After a battle it survived, its new count word is told to the players that see its tiles (`MonsterChanged`, E08 T20b3b1), as the observation shows it.
- **A guarded pile** (E08 T21a, ADV-PIK-004) looks like any pile: its guards, whether it asks before the battle and what a battle left of them are hidden from every player. Its question (an offer to fight) is its visitor's owner's decision, told to it alone; the battle shows that player the guards' stacks, as any battle shows the other side, and its unowned side's events reach no player. What a viewer later sees is the pile itself: picked up after a win, still there after a loss, a retreat or a draw.
- **A surrender's gold** leaves the surrendering side's owner's treasury and enters the other's: each change is told to its owner only.
- **The heroes after a battle** (E08 T19a2a, T19a2b): each change to a hero's details (spell points, experience, an artifact lost with a destroyed war machine, an artifact received or taken in the capture, a spell learned by Eagle Eye) and the creatures its Necromancy raises into its army are told to the hero's owner only (`HeroChanged`): the winner's owner learns the artifacts it captured, as the original's message shows them, and the loser's owner what it lost. Other players see neither, as they never see another player's hero's details (ADV-FOG-006).
- **A player's management of its heroes** (E08 T51a, GAM-MAN-001, GAM-MAN-002): each slot an army command changes, a formation or a tactics flag set and each artifact change are told to the hero's owner only (`StackChanged`, `FormationSet`, `TacticsSet`, `HeroChanged`); the per-hero listing (`legal_management`, `split_range`) answers the actor about its own heroes in its turn and is empty otherwise. Other players learn nothing of it; a meeting's step is a step (its viewers as for any step).

Increment 7 (rewards on the map; `docs/epics/E08-design.md` §13, survey `rules/surveys/E08-rewards.md`) adds:

- **Its own:** what its heroes' visits learned of an object (ADV-VIS-006, E08 T62a): what the game's build drew for it (a Shrine's spell, a Witch Hut's skill, a gift's drawn price, a University's skills) and whether a find is emptied, kept while the object is on the map; and its heroes' once-per-hero marks. No other player learns it. What a chest, an artifact, a box or the Pyramid holds and what the build drew for it are hidden from every player; a visit tells the visitor's owner what it gives.
- **Events** (ADV-FOG-007, E08 T62b2): an event is never observed, whatever the player explored, and nothing tells of one before it fires (paths are blind to it, ADV-MOV-011); its firing is told to the mover's owner alone, then what its guards' battle or its record gives as any visit's.

Increment 8 (boats and the sea; ADR-0016 points 1 and 6, ADR-0017 point 8; `docs/epics/E08-design.md` §12, survey `rules/surveys/E08-sea.md` §9) adds:

- **Boats:** an empty boat is seen where the viewer sees heroes on its tile (ADV-FOG-008, E08 T72): its tile, type and facing, as the original draws it; never its owner or last captain (an empty boat shows no flag) and never its index, which would count the boats before it. A hero in a boat shows its boat's type with the hero (ADV-FOG-006: public, the original draws the hero's flag on it); its day's maximum, as its points, is its owner's only (`OwnHeroView::max_movement`).
- **Events** (E08 T73a, T74a, T74b): a boarding (`Boarded`), a landing (`Landed`, the boat left on its water tile with its facing) and a boat leaving the map with its hero after a battle (`BoatRemoved`, right after `HeroRemoved`) are told to the hero's owner and the players that see heroes on the boat's tile, each naming the boat by its type, never its index, owner or captain; a landing's tile is told by the step's own event to those that see it, so no viewer learns a tile it does not see. A message read (`MessageRead`, the Ocean Bottle) is told to the visitor's owner alone; its text is the client's. The sea's pickups hide their contents as increment 7's finds; their visits and leaving are told as any pickup's.
- **The fog** is unchanged: a boat adds nothing to the scouting radius. A battle at sea is a battle (its owners only), on the deck or the two boats, which the battle's observation shows them.

Increment 9 (mines, the week and owned objects; ADR-0016 points 5 and 6; `docs/epics/E08-design.md` §12, survey `rules/surveys/E08-economy.md` §2.7, §9.4) adds (E08 T83b2b; teams come with E10: until then a player's team is the player alone):

- **Owners:** every viewer sees an ownable object's owner where it sees the object (ADV-OWN-003: the original draws its flag in the owner's colour).
- **A mine's production** (its resource and daily amount) is its owner's team's knowledge only, so an abandoned mine's drawn resource is hidden from every other player, before its flagging and after; a neutral abandoned mine's is no player's.
- **A mine's guards** are seen by every viewer as the original's hint shows them (`mine_hint_text` 0x40D670, `army_description_text` 0x40ABE0): the size word of their total count, every stack counted (an upgraded one too), and their creature only when all stacks are of one; never their stacks, counts or how many stacks. The owner's team sees their stacks and counts. A guarded pile's guards stay hidden from every player (increment 3).
- **A Shipyard's boat tile** is static, and shown only to a viewer of the Shipyard's owner's team (E08 decision 229, ADV-Q40), which has explored every offset the build tried (a flag's reveal, an owned object's at the start); shown to anyone else, the tile would tell which earlier offsets were land or held an object on tiles that viewer may not have explored. A neutral Shipyard's boat tile is no viewer's.
- **A weekly object** (Windmill, Water Wheel, Mystical Garden) shows the viewer its own visited mark (set for the visitor's team, a Garden's too: E08 decision 222, `ADV-QUIRK-35`), kept through the weeks: it says "visited once", never "emptied". Its resource and amount are never shown, before a visit or after.
- **Monsters added in play** (a creature month) are seen as placed ones where their tiles are; a monster's fraction (the sixteenths its weekly growth left) is never shown, its word follows its count.
- **A flag and a mine's visit** (E08 T84a, ADV-OWN-001, ADV-MIN-002): a flag (`ObjectFlagged`: the object by type and anchor and its new owner) is told to every player that sees the object and to its new owner; the tiles it reveals to the new owner alone (`TilesRevealed`, with the number it had not explored). A guarded mine's question is its visitor's owner's alone, as a guarded pile's. An own mine's Leave Guards dialog is its owner's alone: its opening names the mine by type and anchor (`LeaveGuardsOpened`) and then the guards' stacks (`ArmyDialogOpened`), each change the slots it touched (`StackChanged`), its close (`DecisionClosed`); what is left there stays the mine's guards. A change of the guards' hint (their creature when all stacks are of one, the word of their total count, or none left: `GuardsChanged`) is told to every player that sees the mine, never their stacks or counts, and not when the hint stays. A mine's battle is its sides' owners': an owned mine's owner plays the guards' side outside its turn and sees that side's observation, as a hero battle's defender; a neutral mine's side is the neutral seat's. Other players learn of the battle only its effects where they see the mine: the guards' hint, the flag, a hero's leaving the map.
- **A Lighthouse's and a weekly object's visit** (E08 T84b1, ADV-OWN-005, ADV-WEK-001 to -003): a Lighthouse's flag is told as a mine's (`ObjectFlagged`, `TilesRevealed`); the sea points it adds are its owner's heroes' own (each one's movement is its owner's knowledge). A weekly object's visit tells a mark it sets anew to the players whose mark it is (`ObjectMarked`: the visitor's team, a Garden's too since E08 T84b2; not told when the mark was held), then its gain to the visitor's owner alone (`ResourceGained`: the amount, so the owner learns what this week's contents were) or that it was empty (`ObjectEmpty`, the visitor's owner alone). Another player learns neither what it held nor that it was emptied: only the hero's step onto the entrance where it sees the hero.
- **A Shipyard's visit and `BuildBoat`** (E08 T84b2, ADV-SHY-002, ADV-SHY-003): a Shipyard's flag is told as a mine's (`ObjectFlagged`, `TilesRevealed`). Its boat offer is its visitor's owner's alone, as every offer, and so is the reason it makes none (`ShipyardBlocked`: no boat tile, or a boat or a hero on it; the tile's content is what the owner sees there or the static map's). A built boat (`BoatBuilt`: the tile and the boat's type, never its index or owner) is told to its builder and to the players that see heroes on the tile, as they see the empty boat there (ADV-FOG-008); the price paid is the builder's alone (`ResourcePaid`). `BuildBoat` names its Shipyard by type and anchor and is validated against the trusted actor: a Shipyard the player has not explored and a name that is no Shipyard give the same `UnknownObject`, so a command reveals no hidden Shipyard; then its owner must be the player or an ally (`NotOwner`), its tile exist and be free (`NoBoatTile`, `BoatTileTaken`: as the original's message, it tells whether a boat or a hero is on the tile, which the owner has explored with the flag's reveal, its radius 3 in the base pack covering the twelve offsets within 2 of the entrance), and the treasury pay the price, checked before anything changes (`CannotPay`).
- **The week's and a creature month's steps** (E08 T85a, ADV-WEK-001 to -003, ADV-MON-013, ADV-MON-014; the game runs them from T85b): the week refills the weekly objects with no event, as their contents are never shown. A monster's growth tells its new count word to the players that see it (`MonsterChanged`) only when the word changes: a change within the word would tell the count's or the fraction's change, both hidden. A creature month's monster is told to the players that see it as a placed one (`MonsterAdded`: its type, tile, creature and count word; never its index among the objects, its count or its aggression); the walk's draws come from the game's stream, server-only (E08 decision 9).
- **The day's start** (E08 T85b; GAM-CAL-002 to -004, GAM-RES-003 to -005, HER-MAN-002): a week's and a month's start (`WeekStarted`, `MonthStarted` with the month's kind) and the month's kind in the observation (`GameObservation::month`) are public, as the original's messages; the kind and its creature are drawn from the game's stream, server-only. Each player's income is told to it alone (`ResourceGained`, one per resource), so no other player learns its mines' production or its heroes' income; its heroes' regained spell points show only in its own observation, with no event. A map's timed event is its players' own: at each one's turn start its gains and losses (`ResourceGained`; `ResourceLost`, the amount actually taken) and its firing (`TimedEventFired`, by its index in the map's list, which names the message) are told to that player alone, and `GameObservation::events_today` lists the events that fired at the viewer's turn start today (day 1's fire inside the build), never another player's.

Increment 10 (dwellings and hiring; ADR-0016 points 4 and 6, ADR-0017 points 6, 10 and 11; `docs/epics/E08-design.md` §10, §13, survey `rules/surveys/E08-dwellings.md` §9, batch E10's §16) adds (E08 T92; the events' names come with the build, T94 and T95; teams come with E10: until then a player's team is the player alone):

- **A dwelling** shows every viewer that sees it its type (so its name and creatures; a random dwelling's drawn type, footprint and moved anchor, as the original draws it) and its owner (ADV-OWN-003); **never its counts or guards**, before a visit or after, as the original's hint and popup show neither (batch E10's E10-10). A battle's change of its guards and the week's refill are told to no one.
- **A Refugee Camp** shows its type only: its creature and count are hidden from every viewer, from its visitor's owner too once the visit is over (no knowledge kept; VCMI shows a visited camp's creature: not followed, E10-10). Its draws come from the setup's and the game's streams, server-only (E08 decision 9), and are told to no one.
- **A visit's questions and gifts** are the visitor's owner's alone: the guards' question (the guards' first creature and the size word of their total), the hire question (its creatures; a camp's creature), the free creatures joined or refused for want of room, a camp found deserted. The guards' battle is its sides' owners': the guards' side is unowned, the neutral seat's whoever owns the dwelling (ADR-0017 point 11), so an owner learns of a battle at its dwelling only what other viewers do. Other players see its effects where they see the dwelling: the flag (`ObjectFlagged`, its reveal to the new owner alone, as a mine's) and a hero's leaving the map.
- **The hire dialog** (GAM-DEC-008) is its owner's alone: its view (the source by type and anchor, each creature's count and cost) and its purchases (the price paid, `ResourcePaid`; the creatures joined) reach no other player. A purchase is validated against the trusted actor and the open decision, never the payload's price: the creature must be the source's, the amount from 1 to its count, the hero's army must have room and the treasury pay the cost times the amount, each checked before anything changes and refused typed with the state untouched (ADR-0004). An ally's dialog (E10's teams) is read-only, `Close` alone: an ally sees the offer, buys nothing and never flags (the original's disabled dialog, E10-6).

Increment 11 (the teleporters; ADR-0016 points 1, 4, 5 and 6, ADR-0017 points 1, 4, 6 and 11; `docs/epics/E08-design.md` §10, §13, survey `rules/surveys/E08-teleporters.md` §10, batch E11's §15) adds (E08 T102; the events' names come with the build, T105):

- **A teleporter** (a monolith, a Subterranean Gate, a Whirlpool) shows every viewer that sees it its type, so a monolith's channel (the picture's colour, as the original draws it); **never a channel's exits or a gate's pair**, which the static map holds and no view lists: a player learns an exit only by a jump of its own or by seeing a hero arrive there.
- **A jump** is seen as a step's two ends (a new event with the step's fields and projection, ADV-FOG-004 amended): by the players that see the hero on the entrance or on the exit, a viewer that sees one end only told that end and nothing of the other, so no viewer learns a hidden exit (**A-41 not reproduced**: the original's view goes to the exit on a Replay Opponent Turn, batch E11's E11-18). The arrival's reveal (the scouting radius) and an occupied exit's (radius 1, before its battle or meeting) change only the owner's explored tiles, with no event of their own. The exit's draw comes from the acting player's stream, server-only (E08 decision 9); a rejected command leaves the stream untouched (the draw only after every check), so a probing command learns nothing of a draw.
- **To the visitor's owner alone:** a Whirlpool's loss (the stack and its count left), "leads nowhere" (a one-way exit, a gate without a pair; the object by type and anchor), and a gate's meeting with a hero of the team (the meeting's own projection). A monolith without a candidate tells nothing. A battle at an exit is seen as any battle (its sides' owners; other players its effects where they see the tiles: a hero's leaving the map, the jump after a win).
- **`Revisit { hero }`** (the original's space key, ADV-TEL-008) is validated against the trusted actor: the player's turn running with no open decision, the hero the player's and on the map (`NotYourHero`), its tile the visitable tile of an entered object whose kind has a built visit, else one typed `NothingToRevisit` that names nothing but the player's own tile; each refusal leaves the state and the stream untouched. A revisit is told only by what its visit tells (no step event, no reveal of its own); it spends no points, so a client or a rollout may repeat it within a turn (the env's step cap is the AI lane's, ADR-0017 point 8).

### What a viewer may know: a town (E09 increment 1)

The list the town epic owns (ADR-0028; the design note `epics/E09-design.md` §12 and §17,
survey `rules/surveys/E09-towns.md` §12: the original's map picture, hint and right-click popup;
rules TWN-VEW-001 to -003); `h3_game::observe` (`GameObservation::towns`) and `project` implement
it (E09 T8a2, T8b1, T8c1, T8c2), `h3-game`'s `town/tests/view.rs` checks it. Until E10's teams a
player's team is the player alone; a neutral town is nobody's team.

- **Public where the viewer has explored a tile of the town** (a tile only on its fringe gives
  no view): its object links to it (`ObjectView::town`), its owner (the flag), faction, name, fort
  level and whether it has a Capitol. Whether it is defended only as the step and the legal moves
  tell it (a reachable town's cursor).
- **The garrison** to a viewer of another team by its level, the number of the viewer's own towns
  with a standing Tavern, at most 2: 0 nothing, not even whether it is empty; 1 each stack's
  creature, packed in slot order (never the slots); 2 also each stack's size word (the monsters'
  words).
- **The top level** (3): the stacks' counts, the hall level and the day's income (the gold and
  the silo's resources), to the owner's team, and to a viewer one of whose own heroes on the map
  has a Visions creature in its army (the AB pack's Rogue) and stands on the level of the town's
  entrance within its Visions radius (the town part's factor, 3, times the hero's Power, at least
  3; E09 T8c2), as the original's popup shows them. The garrison by slot (the town screen's,
  which the garrison's `StackChanged` events change) is the owner's team's only.
- **Never public:** the town's other buildings, its ever-built and forbidden sets, the Escape
  Tunnel and the defender's bonuses; a merge's stacks (the visitor's owner's); a draw's values
  (a random town's faction before it is seen, a neutral garrison, the start's dwelling), drawn
  from server-only streams.
- **Events:** a capture (`TownCaptured`) and a change of the town's picture (`TownChanged`) to the
  players that see the town and to its new owner; the capture's reveal to the new owner alone
  (`TilesRevealed`). A siege is told as any battle, to its sides' owners; others learn its
  effects where they see the town. The day's income is told to its owner alone, in its
  `ResourceGained` with the mines' and the heroes'.
- **A town's `TownId`** (ADR-0028 point 3: its index among the map's towns in object order) names
  it in the views and events, so a seen town's id tells how many towns come before it in object
  order, seen or not. Kept, as ADR-0028 point 3 names a town by it in the commands, events and
  observations (unlike an object, named by type and anchor); in the original each player of a
  game holds the map file, which lists the same towns.

### A town's construction (E09 increment 2)

ADR-0028 points 2 and 6, ADR-0017 points 1, 2 and 10, ADR-0016 point 6 (E09 decisions 42, 45,
47; the design note `epics/E09-design.md` §29 and §31; rule TWN-VEW-004). The build task
(E09 T18b) implements it; `h3-game`'s view tests and the hygiene and told-views properties check
it with builds.

- **The build is the owner's** (`GameCommand::Town(TownCommand::Build { town, building })`):
  the actor must own the town and be in its turn with no open decision; the price is the
  building's cost from the town part, paid from the actor's own treasury, never named by the
  command. The original's build dialog refuses any other player (batch TWN-2, survey
  `rules/surveys/E09-construction.md` §13), so no visitor spends its own or another player's
  resources in a town it does not own. A refused build changes nothing.
- **Public where the town is seen:** as increment 1's, plus **whether it was built in today**
  (the popup's portrait); its fort level and Capitol change with a build.
- **The owner's:** the town's buildings (ever built, forbidden, so the standing ones) and the
  legal builds, as the town screen opens from the town list at any time. Not the owner's team,
  not Visions' top level (the popup shows no buildings).
- **An ally's visit** (E10's teams; until then no town is an ally's): the entering step tells
  the visiting player the town's buildings once, as the original's town screen opens at the
  visit.
- **Never public:** another player's town's buildings and legal builds; the town's boat spot
  (increment 4 places its view as a Shipyard's boat tile, the owner's team).
- **Events:** a build and a town event's buildings (`TownBuilt`) and a town event's firing
  (`TownEventFired`) to the owner alone, its resources in the owner's `ResourceGained` and
  `ResourceLost`; a change of the town's public facts (fort, Capitol, built today; `TownChanged`)
  to the players that see the town, its top level's facts (hall, income) only to the viewers at
  that level. A new Tavern raises its owner's view level of every other town, told by its
  `TownBuilt`.

## Denial of service and resource limits

- Bounded command size and count per turn; bounded work per command (path search limits, list lengths).
- Deterministic termination: loops in rules must have ruleset-defined bounds.
- Memory bounds for map/archive parsing; reject dimensions or counts above configured limits.
- Arithmetic: checked/saturating operations wherever overflow is possible; no panics on external input (enforced via the lint policy in `05-testing.md`).
- Rate limiting, connection handling and authentication are the server's job ("Hosted games" below); the core supplies bounded, panic-free primitives.

## Hosted games (the server, E16, ADR-0018)

The server (`h3-server`, the I/O shell around `h3-protocol`'s sans-I/O session core) is the first surface where untrusted clients send commands. It adds no rules; it guarantees:

- **Identity is the connection's seat** (ADR-0018 point 6). A connection becomes a seat's actor by taking it: the first time without a token (the server hands the seat's token out in `Joined`), afterwards only with that token, 128 bits of OS randomness compared in a time independent of where it differs. Commands name no side or player (a command with such a field does not decode); the session applies them with the seat's side. A connection without a seat is no actor (`NotSeated`). Since E16 M3 T3 a seat a logged-in connection takes belongs to its account: any connection logged in as it re-takes the seat, no token and no other account takes it, and its `Joined` carries no token (the journal's copy of the seat's token takes nothing); a seat an anonymous connection takes keeps its token.
- **Accounts** (E16 M3, ADR-0019 point 1; `E16-design.md` §10): a login name and a password derive an Ed25519 key on the client (Argon2id, salted by the login name); the server stores the login name, the public key and the display name in its player log, never a password or a hash of one. A login signs the server's id (the address its clients dial, `public_url`) and a challenge drawn per connection from the OS, so it can be neither replayed nor relayed to another server; signatures are checked strictly (no small-order key, no malleable signature), and a refusal does not say whether the name, the key or the signature failed. A re-key needs both keys' signatures and closes the account's other connections logged in with another key (`Rekeyed`); a rename or a preference from a connection whose key the account re-keyed from meanwhile is refused (checked under the player log's lock); a forgotten password is rebound by the operator while the server is stopped (`h3-server rebind`, the data directory's lock). Failed logins (10 a minute) and requests that may write the player log (20 an hour: registrations, re-keys, renames, preferences) count per address, beyond its connections' lifetimes; beyond them a request closes its connection (`RateLimited`). Each change is synced to the log before its answer, and a refused one's line is cut off again. Other clients see display names only (unique ignoring case); a login name and a key are shown to their owner. Without a login a connection plays anonymously where `[server] anonymous` allows (the default).
- **A rejected command changes nothing**: neither the battle nor the journal, and the other seat hears nothing; while the battle runs, the seat not to act gets `NotYourTurn`. Property-tested over the wire in `h3-protocol`.
- **Everything outbound is projected per viewer by construction** (point 7): the mapping's observation and events take the viewer and call the engine's `observe` and `project`; the unprojected conversion is private to it. Every accepted command gives every viewer an `Events` message, even an empty one, so the shape of a viewer's stream does not depend on what it may not see. A spectator (E16 M2 T4) gets the battle's spectator viewer: what is public to both sides, neither hero's private part, never a token, a turn or the replay. Property-tested: a hidden cast leaves the other viewer's and the spectators' bytes equal for any two seeds.
- **Secrets stay on the server** (point 8). The tools derive the visible random obstacles and the hidden battle RNG from one seed (different streams), so a seed a client could guess from the layout would predict every roll. The server therefore draws the battle's seed as 64 bits of OS randomness, independent of anything a client sees, and the obstacles from a separate seed that is used once and forgotten; the obstacles enter the setup as pieces, so no journal or replay holds an obstacle seed. Seeds, RNG state, state hashes and tokens never reach a client or a log line (a token reaches only the client that takes its seat, in `Joined`). The replay (seed, setup, every command) reaches no one before the battle ends (`NotOver`); until then a viewer may fetch its *record*, the log of what it was sent. Afterwards it is public (E16 M2 T5d, SRV-Q15): a verified game's replay joins the server's archive, which any client lists and downloads from without a game, by an id the archive names (a client never names a file); a game its host closed to spectators, or one of whose seated accounts opted out of the listing (E16 M3 T3, ADR-0019 point 2), is archived unlisted; the archive keeps at most `replays_kept` (10 000) replays in each part, the oldest deleted.
- **Bounds, all configured** (point 9; `[limits]` in the configuration, defaults in parentheses): the frame size (4 096 bytes, checked before parsing; a frame far over it is dropped unread), messages per second per connection (20) and across one address's connections (40; E16 M2 T5b), WebSocket pings included, then `RateLimited`, connections in total (64) and per address (8, refused before the handshake), the idle timeout (no message from the client for 300 s; it also bounds a stalled write and the handshake), the server's own pings (every 15 s; a connection it heard nothing from, not even a pong, for 30 s closes, `IdleTimeout`; E16 SRV-Q20: a connection that died silently frees its seat within seconds), the hello (10 s after the handshake) and the time in no game (60 s after the hello or after leaving a game it was in; E16 M2 T5b; a refused join does not restart it, T5e), so a connection that never joins does not keep its counted place, the outbound queue per connection (256 frames and 2 MiB, E16 M2 T5c: a client too slow to read is dropped, `TooSlow`, never buffered for), a viewer's record (its latest messages within 512 KiB, E16 M2 T5c; `FetchRecord` sends that window), the games that are not over, in total (16) and created from one address (2; each game is a thread; E16 M2 T1); a running game none of whose seats is held for 30 minutes pauses, and a paused one nobody resumes within 72 hours is void (E16 M2 T5a); a waiting game none of whose seats is held leaves at once, also with spectators watching (E16 M3 T4a); a game that reaches 10 000 commands without an end is void (E16 M3 T4a: `CommandLimit`, no replay), which bounds its journal, its memory and its replay, the archived one included, and the configuration refuses a limit whose replay would not fit the outbound queue. The limits per address count an IPv6 address by its /64 prefix, and a connection from a configured reverse proxy (`trusted_proxies`) as the client the last entry of its `X-Forwarded-For` names; a forwarded header from any other peer is ignored (E16 M3 T4b). A client creates games only from the server's offers, never from a setup of its own. One command in flight per seat holds by construction: the game's thread handles one message at a time. A malformed, binary, oversized or out-of-place message closes the connection with its reason; decoding never panics (property-tested on arbitrary bytes and on mutated valid messages, E16 M2 T5d; a coverage-guided fuzzer later, `05-testing.md`).
- **One ruleset, the server's** (point 10): clients run no rules in a hosted game, and the server trusts no client-computed value; the manifest at join names the content.
- **The journal and the data directory** (point 12; E16 M2 T2): every accepted command, every seat taken and the start are written to the game's journal and synced before anything that depends on them is sent, so a restart re-runs the game to exactly what its players were told; a journal whose engine or content identity is not the server's, or that does not re-run to its recorded hashes, restores nothing (it is moved aside, void). The journal holds the battle's seed and the seats' tokens (the operator's copy, for a player who lost its `Joined`): the data directory is as trusted as the server's memory and must be readable by the server's user only (on Unix the server creates its directories owner-only and the journals owner-read-write). Errors about a journal name its line, never its text. Since E16 M6 it also holds the server's key (below), its one secret beyond the games: whoever reads it can speak as the server, not as a player.
- **Integrity** (point 12; E16 M2 T3): a finished game's journal is read back from disk and re-run in a fresh battle before its replay is published; every checkpoint, the live game's final state hash and result must match, and the ruleset in memory must still hash to its content hash. A game that does not verify is void: its replay is withheld (`Unverified`), the journal and the replay as played, with the diagnosis, are kept in `<data>/void/`, and the log line names the step, never a hash. An optional shadow instance applies every command to a second battle and, if the two differ, rebuilds both from the journal before anything is sent.
- **Pause** (E16 M2 T3): only the host (the seat taken first) pauses a running unranked game (the other seat may ask it once until the game moves on, E16 M4 T6; a ranked game's pause below); a paused game is its journal, and only a seat's token, or for an account's seat its account (E16 M3 T3), resumes it: the server checks either before it re-runs the journal, so a stranger cannot make it restore a paused game.
- **Ladders and ranked games** (E16 M4, ADR-0019 points 4–9; `E16-design.md` §11): only a logged-in account queues, in one ladder's queue at a time, and never while its ranked game on that ladder is unfinished (running or paused); a client names the ladder and whether it accepts a bot, nothing else: the server pairs players by the ratings it holds, draws the scenario from the ladder's pool and the sides with OS randomness, and binds both seats to the accounts (journaled) before any join reaches the game, so no other connection takes them. A ranked game has no host: a pause needs both seats (one proposes within the ladder's count and length, the other agrees, E16 M4 T6). An absent seat is timed by the server's clock only (a grace per absence, a total per game; the server's own downtime never counts, and its pings notice a dead connection); beyond either the player forfeits, and both away make the game void and unrated. Results are rated by the server alone, after the game's journal re-ran from disk (a game that does not verify is void, unrated, its players told), written once to the ladder's results log (synced, read back at start, never recomputed; a game's id is never handed out twice), and the clients see ratings as whole numbers. The server's bots play from accounts without a key (no login, re-key or rebind reaches them) and are flagged wherever a player meets them (the ladder list, the lobby, `MatchFound`, the leaderboard); a player may queue for people only. Leaderboards show display names, never login names or keys. The queues hold one entry per queued account, in memory; a seat asks for a pause once until the game moves on.
- **Server identity and discovery** (E16 M6, ADR-0021; `E16-design.md` §12): the server's Ed25519 key (`<data>/server.key`, written owner-read-write at the first start, never replaced; a key file that does not read stops the start) is its identity across addresses. Its welcome signs the client's nonce, the server's id on that connection (the address the client dialed when it is one of the server's own, its `public_url` otherwise; a client refuses an id that is not the address it dialed) and the connection's challenge, so a client that pins the key per address knows that the key's holder answered there; it does not prove that nobody sits between (TLS does). Every signed text starts with its purpose and version (`h3-welcome-v1`, `h3-card-v1`, `h3-list-v1`, and the logins' `h3-login-v1`), so no signature serves two purposes, and every signature is checked strictly, as a login's is. The card (`Describe`, after the hello, no login needed) is the server's own signed word about itself, relayed verbatim as signed; a reader accepts it within its bounds (8 KiB of text, at most 8 addresses, 64 peers, 16 rulesets, 16 ladders), from its issue time (at most 10 minutes ahead of the reader's clock) to its expiry (a day by default). Its counts are public to anyone who asks unless `[discovery] counts = false`. The server dials only the addresses its configuration names (its `[[peer]]`s and the servers its lists name), never one it read in a card: one fetch at a time, each within `timeout_ms`, its frames and their total bounded; it takes a card only from the key configured for the address, whose welcome names that address. A card a peer relays is kept only if it verifies and each link of its vouching chain (`via`) holds from the peer's own card, within `depth` hops and at most `cards` of each peer's cards; what the server relays is checked again against what it serves, so a client can check every chain from the cards it receives (`card::chain`), and a card is relayed only until the first card of its chain expires. A list of servers is signed by its own key and read from `<data>/lists/` (32 KiB, 128 servers, at most 16 lists; a forged, malformed or expired list, or a second of one key, is skipped and logged); its servers are fetched as peers are, their own cards only, relayed marked with the list's key, and `Lists` gives the lists, so a client checks that one names each such card. A peer's list stays the peer's: what it relays for a list is not relayed on. Vouching says who vouches, not whether a server is good: the client shows the chain and contacts a server only on the player's choice (the client lane's).
- **Exposure**: the server binds loopback by default; on the internet it runs behind a TLS-terminating reverse proxy (E16 M3 T4b, the operator's setup in `crates/h3-server/README.md`), with `public_url` naming the address clients dial and the proxy among `trusted_proxies`. Logins are safe without TLS (a signed challenge is no secret); a session's integrity is not. Since E16 M6 the server also dials out, to the addresses above only: at `wss://` through its own TLS client (`rustls` with the pure-Rust graviola backend, certificates checked against the operating system's roots; ADR-0018 point 2 as amended, ADR-0021 point 4), at `ws://` on a LAN.
- **Not covered yet**: a waiting game whose creator stays seated has no deadline of its own (the limit of games per address bounds it); a host with more than one /64 (a /48 holds 65 536) counts as many addresses; the player log's readers (every login) wait behind a change's sync, bounded by the changes' rate; a connected player may stall a ranked battle on its turn (no turn timer before the game's rules bring one, M5, SRV-Q19); a seat may forfeit within a ping period of a server-side drop that took the other seat's connection too (SRV-Q20); colluding accounts trading wins, or one person's many accounts, are not detected (the changes per address bound the registrations); a battle's hidden draws (pit and mine hexes, a random caster's drawn spell, Eagle Eye) come from the same generator as its public rolls, seeded from 64 bits, so a client that recovers the generator's state from the public rolls knows them (E04b's security review: a keyed stream for hosted games, `h3-kernel`, when the server needs it); timing and message-size side channels (bounded by projection and the stream's fixed shape; timing is out of scope for now). Discovery (E16 M6): a server key cannot be revoked (a leaked one speaks as the server until each player changes the pin by hand; a lost one is a new identity whose welcome every pin refuses), nor a list before its expiry (up to 366 days; the operators serving it remove its file); a card's claims beyond its signature and bounds (its counts, rulesets, ladders) are its server's word alone; a peer of another protocol version cannot be fetched (no version negotiation before 1.0); any client may ask, after its hello, for a page of up to 50 relayed cards or the lists per message, bounded by the message rates and by the client reading each answer before its next message is handled; the graviola backend is young and runs on x86_64 and aarch64 with their crypto extensions only (elsewhere every `wss://` fetch fails, logged).

## Untrusted files

Maps, archives, and saves are attacker-controlled input. `h3-formats` parsers: no `unsafe`, strict bounds checking, length limits, graceful errors, to be fuzzed (`05-testing.md`: not set up yet). Anything that becomes domain state passes the same validation as if commands had built it (e.g., a map cannot start with negative resources or overlapping stacks beyond the limits).

## Security regression policy

- Every known exploit class gets a quirks-ledger entry (`exploit-fix`) and a named regression test that attempts the exploit and asserts rejection.
- Property tests for ownership isolation and observation hygiene (see `05-testing.md`) run on every context.
- Adding a command requires writing its validation, rejection tests, and visibility scope in the same change. The DoD checklist enforces this.

## Out of scope for the core

Transport encryption, authentication protocols, account management, matchmaking, client integrity/anti-tamper on the client side. These belong to server and client layers; the core only guarantees that a correct server cannot be tricked via valid-looking commands and that it can avoid leaking hidden state.
