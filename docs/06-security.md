# 06 — Security and anti-cheat design

## Scope

The original game had exploits such as spending another player's resources in your town, and in networked play the client held far more information than the player should see. The engine must make that class of bug structurally hard.

Protections apply to the **authoritative (server) mode**: a trusted engine instance with untrusted clients. In local single-player or hotseat with an embedded engine, the local user is trusted (hotseat hiding is a UI concern). The design works in both because the same API is used.

## Trust boundaries

```
untrusted client ──bytes──▶ [transport/decoder adapter] ──typed Command──▶ [session: authenticates → Actor] ──▶ game.apply(actor, command)
untrusted files  ──bytes──▶ [formats adapter: validates, bounds, converts] ──▶ domain types
                                                              game state ──▶ [observe/project per viewer] ──▶ client
```

1. **Identity comes from the session, never from the payload.** The `Actor` passed to `apply` is created by the trusted session layer from the authenticated connection. Commands never contain "who I am" or "whose resources to use".
2. **Commands carry intent only.** No prices, resource amounts, ownership claims, derived stats or results. Everything derivable is computed from state. Example: `BuildStructure { town, structure }` — cost and payer come from the ruleset and the actor's own treasury.
3. **Validation is total and centralized.** `apply` checks: it is the actor's turn/phase, the actor owns every referenced entity (or the interaction is explicitly modelled), all references exist, preconditions hold, resource checks use the *actor's* stock, bounds hold. The validator runs before any mutation; on failure state is unchanged (atomicity is property-tested).
4. **No reach-through.** Domain functions receive the minimal capability they need (e.g., the actor's own treasury handle), not the whole state plus an id, which makes cross-player access impossible to express by accident.
5. **Legal-command consistency.** `legal_commands` and `apply` share one precondition implementation (or are tested equivalent), so UI hints can't diverge from enforcement.

## Information hiding

- The server never sends full state to a client. It sends `Observation`s and events **projected per viewer**: every event has a visibility scope; `project(event, viewer)` drops or redacts what the viewer may not know.
- Fog of war, unexplored tiles, opponents' unseen armies/heroes/resources, hidden object contents, and opponents' private decisions are excluded from projections. Define per context what each viewer may know (adventure context epic owns the list).
- **Lockstep-with-full-state multiplayer is excluded** by design: every client would hold the complete state and could read everything.
- **Clients therefore need a view model** that applies projected events to partial state. Keeping client code out of the core (ADR-0005) makes this a client concern, but projections are a core contract.
- **Side channels to consider:** RNG seed/stream state must not reach clients (it predicts rolls); saves and replays are exported *per viewer* (redacted) unless the requester is authorized (e.g., post-game); state hashes must not be computed over, or exposed in a form that leaks, hidden data; error messages must not reveal hidden facts ("no such hidden object at tile X" vs. "invalid").
- **Hotseat** hiding is UI-level and out of scope for the core.

### What a viewer may know: the adventure map (E08)

The list the adventure epic owns (ADR-0016 points 5 and 6, ADR-0017 point 5); `h3_game::observe` and `project` implement it (E08 T8b1), the property tests of E08 T8b2 check it. A player viewer:

- **Public facts:** the map's size and levels, the day, the turn group whose turn is running and which of its players still act, each player's colour; the ruleset (its profile included).
- **Its own:** its explored tiles and their fringe (the hidden tiles touching an explored one, ADV-FOG-005), and its heroes in full: tile, army, movement points left.
- **Explored tiles** show their current content (ADV-FOG-004): terrain, road, river, what objects cover there (blocked and visitable tiles), and the heroes standing there.
- **The fringe** shows terrain, roads and rivers. Under `ADV-QUIRK-1` (the `faithful` profile) it also shows what objects cover there and the heroes standing there: an object's appearance is public there while its contents stay hidden (increment 1's objects have none; contents come with increment 2's objects).
- **Another player's hero**, where the viewer sees its tile: its tile, owner and identity, never its army or movement points (ADV-FOG-006; what the original's right-click view shows comes with the battle seam).
- **Events:** a hero's step is told to its owner and to the players who see the hero on the tile it leaves or enters, so the viewer learns of a move only where it can see it; a viewer that sees the hero on one of the two tiles is told that tile only. A projected event names the viewer alone, since the full set of its viewers would tell which tiles other players explored. A move is refused onto an unexplored tile before anything else about that tile is checked (ADV-MOV-008), so a rejection says nothing about a hidden tile.
- **Never:** any other tile, other players' explored tiles, the master seed, the streams, the state hash. A viewer that is not a player of the game sees the public facts and no tile.

Increment 2 (objects, the treasury, offers; ADR-0016 points 4–6, ADR-0017 points 1, 6 and 10; survey `rules/surveys/E08-objects.md` §8) adds:

- **Typed objects** are seen whole (type, anchor, masks) once any tile they cover is explored, or on the fringe under `ADV-QUIRK-1` (E08 T12b). The type is public, a random resource's drawn resource included (its picture shows it). Never their contents: a pile's or campfire's amount, a campfire's resource. Objects are listed in map order, never by index: an index counts the objects before it, seen or not.
- **Its own:** its treasury (E08 T13; other players' treasuries are hidden: the Thieves' Guild comes with towns); its per-object state, the Cartographer kinds bought and the keys held (T14, T15); its open decision, kind and price (T14).
- **Events:** a pickup tells its owner the gain (the treasury's change); an object leaving the map is told to every player who sees it there, as the observation shows it (T13). A reveal tells the visitor its new explored tiles only (T14, T15). A border guard's removal and a hero on a border gate are public where the tiles are seen (T15). An offer's opening or refusal (the price not payable), its answer and the price paid are told to its owner only, and a Cartographer's reveal tells it how many tiles it explored; a visit to a kind already bought tells nothing (T14).

## Denial of service and resource limits

- Bounded command size and count per turn; bounded work per command (path search limits, list lengths).
- Deterministic termination: loops in rules must have ruleset-defined bounds.
- Memory bounds for map/archive parsing; reject dimensions or counts above configured limits.
- Arithmetic: checked/saturating operations wherever overflow is possible; no panics on external input (enforced via the lint policy in `05-testing.md`).
- Rate limiting, connection handling and authentication are the server's job ("Hosted games" below); the core supplies bounded, panic-free primitives.

## Hosted games (the server, E16, ADR-0018)

The server (`h3-server`, the I/O shell around `h3-protocol`'s sans-I/O session core) is the first surface where untrusted clients send commands. It adds no rules; it guarantees:

- **Identity is the connection's seat** (ADR-0018 point 6). A connection becomes a seat's actor by taking it: the first time without a token (the server hands the seat's token out in `Joined`), afterwards only with that token, 128 bits of OS randomness compared in a time independent of where it differs. Commands name no side or player (a command with such a field does not decode); the session applies them with the seat's side. A connection without a seat is no actor (`NotSeated`). Since E16 M3 T3 a seat a logged-in connection takes belongs to its account: any connection logged in as it re-takes the seat, no token and no other account takes it, and its `Joined` carries no token (the journal's copy of the seat's token takes nothing); a seat an anonymous connection takes keeps its token.
- **Accounts** (E16 M3, ADR-0019 point 1; `E16-design.md` §10): a login name and a password derive an Ed25519 key on the client (Argon2id, salted by the login name); the server stores the login name, the public key and the display name in its player log, never a password or a hash of one. A login signs the server's id (the address its clients dial, `public_url`) and a challenge drawn per connection from the OS, so it can be neither replayed nor relayed to another server; signatures are checked strictly (no small-order key, no malleable signature), and a refusal does not say whether the name, the key or the signature failed. A re-key needs both keys' signatures and closes the account's other connections logged in with another key (`Rekeyed`); a rename or a preference from a connection whose key the account re-keyed from meanwhile is refused (checked under the player log's lock); a forgotten password is rebound by the operator while the server is stopped (`h3-server rebind`, the data directory's lock). Failed logins (10 a minute) and requests that may write the player log (20 an hour: registrations, re-keys, renames, preferences) count per address, beyond its connections' lifetimes; beyond them a request closes its connection (`RateLimited`). Each change is synced to the log before its answer, and a refused one's line is cut off again. Other clients see display names only (unique ignoring case); a login name and a key are shown to their owner. Without a login a connection plays anonymously where `[server] anonymous` allows (the default).
- **A rejected command changes nothing**: neither the battle nor the journal, and the other seat hears nothing; while the battle runs, the seat not to act gets `NotYourTurn`. Property-tested over the wire in `h3-protocol`.
- **Everything outbound is projected per viewer by construction** (point 7): the mapping's observation and events take the viewer and call the engine's `observe` and `project`; the unprojected conversion is private to it. Every accepted command gives every viewer an `Events` message, even an empty one, so the shape of a viewer's stream does not depend on what it may not see. A spectator (E16 M2 T4) gets the battle's spectator viewer: what is public to both sides, neither hero's private part, never a token, a turn or the replay. Property-tested: a hidden cast leaves the other viewer's and the spectators' bytes equal for any two seeds.
- **Secrets stay on the server** (point 8). The tools derive the visible random obstacles and the hidden battle RNG from one seed (different streams), so a seed a client could guess from the layout would predict every roll. The server therefore draws the battle's seed as 64 bits of OS randomness, independent of anything a client sees, and the obstacles from a separate seed that is used once and forgotten; the obstacles enter the setup as pieces, so no journal or replay holds an obstacle seed. Seeds, RNG state, state hashes and tokens never reach a client or a log line (a token reaches only the client that takes its seat, in `Joined`). The replay (seed, setup, every command) reaches no one before the battle ends (`NotOver`); until then a viewer may fetch its *record*, the log of what it was sent. Afterwards it is public (E16 M2 T5d, SRV-Q15): a verified game's replay joins the server's archive, which any client lists and downloads from without a game, by an id the archive names (a client never names a file); a game its host closed to spectators, or one of whose seated accounts opted out of the listing (E16 M3 T3, ADR-0019 point 2), is archived unlisted; the archive keeps at most `replays_kept` (10 000) replays in each part, the oldest deleted.
- **Bounds, all configured** (point 9; `[limits]` in the configuration, defaults in parentheses): the frame size (4 096 bytes, checked before parsing; a frame far over it is dropped unread), messages per second per connection (20) and across one address's connections (40; E16 M2 T5b), WebSocket pings included, then `RateLimited`, connections in total (64) and per address (8, refused before the handshake), the idle timeout (no message from the client for 300 s; it also bounds a stalled write and the handshake), the server's own pings (every 15 s; a connection it heard nothing from, not even a pong, for 30 s closes, `IdleTimeout`; E16 SRV-Q20: a connection that died silently frees its seat within seconds), the hello (10 s after the handshake) and the time in no game (60 s after the hello or after leaving a game it was in; E16 M2 T5b; a refused join does not restart it, T5e), so a connection that never joins does not keep its counted place, the outbound queue per connection (256 frames and 2 MiB, E16 M2 T5c: a client too slow to read is dropped, `TooSlow`, never buffered for), a viewer's record (its latest messages within 512 KiB, E16 M2 T5c; `FetchRecord` sends that window), the games that are not over, in total (16) and created from one address (2; each game is a thread; E16 M2 T1); a running game none of whose seats is held for 30 minutes pauses, and a paused one nobody resumes within 72 hours is void (E16 M2 T5a); a waiting game none of whose seats is held leaves at once, also with spectators watching (E16 M3 T4a); a game that reaches 10 000 commands without an end is void (E16 M3 T4a: `CommandLimit`, no replay), which bounds its journal, its memory and its replay, the archived one included, and the configuration refuses a limit whose replay would not fit the outbound queue. The limits per address count an IPv6 address by its /64 prefix, and a connection from a configured reverse proxy (`trusted_proxies`) as the client the last entry of its `X-Forwarded-For` names; a forwarded header from any other peer is ignored (E16 M3 T4b). A client creates games only from the server's offers, never from a setup of its own. One command in flight per seat holds by construction: the game's thread handles one message at a time. A malformed, binary, oversized or out-of-place message closes the connection with its reason; decoding never panics (property-tested on arbitrary bytes and on mutated valid messages, E16 M2 T5d; a coverage-guided fuzzer later, `05-testing.md`).
- **One ruleset, the server's** (point 10): clients run no rules in a hosted game, and the server trusts no client-computed value; the manifest at join names the content.
- **The journal and the data directory** (point 12; E16 M2 T2): every accepted command, every seat taken and the start are written to the game's journal and synced before anything that depends on them is sent, so a restart re-runs the game to exactly what its players were told; a journal whose engine or content identity is not the server's, or that does not re-run to its recorded hashes, restores nothing (it is moved aside, void). The journal holds the battle's seed and the seats' tokens (the operator's copy, for a player who lost its `Joined`): the data directory is as trusted as the server's memory and must be readable by the server's user only (on Unix the server creates its directories owner-only and the journals owner-read-write). Errors about a journal name its line, never its text. Since E16 M6 it also holds the server's key (below), its one secret beyond the games: whoever reads it can speak as the server, not as a player.
- **Integrity** (point 12; E16 M2 T3): a finished game's journal is read back from disk and re-run in a fresh battle before its replay is published; every checkpoint, the live game's final state hash and result must match, and the ruleset in memory must still hash to its content hash. A game that does not verify is void: its replay is withheld (`Unverified`), the journal and the replay as played, with the diagnosis, are kept in `<data>/void/`, and the log line names the step, never a hash. An optional shadow instance applies every command to a second battle and, if the two differ, rebuilds both from the journal before anything is sent.
- **Pause** (E16 M2 T3): only the host (the seat taken first) pauses a running unranked game (the other seat may ask it once until the game moves on, E16 M4 T6; a ranked game's pause below); a paused game is its journal, and only a seat's token, or for an account's seat its account (E16 M3 T3), resumes it: the server checks either before it re-runs the journal, so a stranger cannot make it restore a paused game.
- **Ladders and ranked games** (E16 M4, ADR-0019 points 4–9; `E16-design.md` §11): only a logged-in account queues, in one ladder's queue at a time, and never while its ranked game on that ladder is unfinished (running or paused); a client names the ladder and whether it accepts a bot, nothing else: the server pairs players by the ratings it holds, draws the scenario from the ladder's pool and the sides with OS randomness, and binds both seats to the accounts (journaled) before any join reaches the game, so no other connection takes them. A ranked game has no host: a pause needs both seats (one proposes within the ladder's count and length, the other agrees, E16 M4 T6). An absent seat is timed by the server's clock only (a grace per absence, a total per game; the server's own downtime never counts, and its pings notice a dead connection); beyond either the player forfeits, and both away make the game void and unrated. Results are rated by the server alone, after the game's journal re-ran from disk (a game that does not verify is void, unrated, its players told), written once to the ladder's results log (synced, read back at start, never recomputed; a game's id is never handed out twice), and the clients see ratings as whole numbers. The server's bots play from accounts without a key (no login, re-key or rebind reaches them) and are flagged wherever a player meets them (the ladder list, the lobby, `MatchFound`, the leaderboard); a player may queue for people only. Leaderboards show display names, never login names or keys. The queues hold one entry per queued account, in memory; a seat asks for a pause once until the game moves on.
- **Server identity and discovery** (E16 M6, ADR-0021; `E16-design.md` §12): the server's Ed25519 key (`<data>/server.key`, written owner-read-write at the first start, never replaced; a key file that does not read stops the start) is its identity across addresses. Its welcome signs the client's nonce, the server's id on that connection (the address the client dialed when it is one of the server's own, its `public_url` otherwise; a client refuses an id that is not the address it dialed) and the connection's challenge, so a client that pins the key per address knows that the key's holder answered there; it does not prove that nobody sits between (TLS does). Every signed text starts with its purpose and version (`h3-welcome-v1`, `h3-card-v1`, `h3-list-v1`, and the logins' `h3-login-v1`), so no signature serves two purposes, and every signature is checked strictly, as a login's is. The card (`Describe`, after the hello, no login needed) is the server's own signed word about itself, relayed verbatim as signed; a reader accepts it within its bounds (8 KiB of text, at most 8 addresses, 64 peers, 16 rulesets, 16 ladders), from its issue time (at most 10 minutes ahead of the reader's clock) to its expiry (a day by default). Its counts are public to anyone who asks unless `[discovery] counts = false`. The server dials only the addresses its configuration names (its `[[peer]]`s and the servers its lists name), never one it read in a card: one fetch at a time, each within `timeout_ms`, its frames and their total bounded; it takes a card only from the key configured for the address, whose welcome names that address. A card a peer relays is kept only if it verifies and each link of its vouching chain (`via`) holds from the peer's own card, within `depth` hops and at most `cards` of each peer's cards; what the server relays is checked again against what it serves, so a client can check every chain from the cards it receives (`card::chain`), and a card is relayed only until the first card of its chain expires. A list of servers is signed by its own key and read from `<data>/lists/` (32 KiB, 128 servers, at most 16 lists; a forged, malformed or expired list, or a second of one key, is skipped and logged); its servers are fetched as peers are, their own cards only, relayed marked with the list's key, and `Lists` gives the lists, so a client checks that one names each such card. A peer's list stays the peer's: what it relays for a list is not relayed on. Vouching says who vouches, not whether a server is good: the client shows the chain and contacts a server only on the player's choice (the client lane's).
- **Exposure**: the server binds loopback by default; on the internet it runs behind a TLS-terminating reverse proxy (E16 M3 T4b, the operator's setup in `crates/h3-server/README.md`), with `public_url` naming the address clients dial and the proxy among `trusted_proxies`. Logins are safe without TLS (a signed challenge is no secret); a session's integrity is not. Since E16 M6 the server also dials out, to the addresses above only: at `wss://` through its own TLS client (`rustls` with the pure-Rust graviola backend, certificates checked against the operating system's roots; ADR-0018 point 2 as amended, ADR-0021 point 4), at `ws://` on a LAN.
- **Not covered yet**: a waiting game whose creator stays seated has no deadline of its own (the limit of games per address bounds it); a host with more than one /64 (a /48 holds 65 536) counts as many addresses; the player log's readers (every login) wait behind a change's sync, bounded by the changes' rate; a connected player may stall a ranked battle on its turn (no turn timer before the game's rules bring one, M5, SRV-Q19); a seat may forfeit within a ping period of a server-side drop that took the other seat's connection too (SRV-Q20); colluding accounts trading wins, or one person's many accounts, are not detected (the changes per address bound the registrations); a battle's hidden draws (pit and mine hexes, a random caster's drawn spell, Eagle Eye) come from the same generator as its public rolls, seeded from 64 bits, so a client that recovers the generator's state from the public rolls knows them (E04b's security review: a keyed stream for hosted games, `h3-kernel`, when the server needs it); timing and message-size side channels (bounded by projection and the stream's fixed shape; timing is out of scope for now). Discovery (E16 M6): a server key cannot be revoked (a leaked one speaks as the server until each player changes the pin by hand; a lost one is a new identity whose welcome every pin refuses), nor a list before its expiry (up to 366 days; the operators serving it remove its file); a card's claims beyond its signature and bounds (its counts, rulesets, ladders) are its server's word alone; a peer of another protocol version cannot be fetched (no version negotiation before 1.0); any client may ask, after its hello, for a page of up to 50 relayed cards or the lists per message, bounded by the message rates and by the client reading each answer before its next message is handled; the graviola backend is young and runs on x86_64 and aarch64 with their crypto extensions only (elsewhere every `wss://` fetch fails, logged).

## Untrusted files

Maps, archives, and saves are attacker-controlled input. `h3-formats` parsers: no `unsafe`, strict bounds checking, length limits, graceful errors, to be fuzzed (`05-testing.md`: not set up yet). Anything that becomes domain state passes the same validation as if commands had built it (e.g., a map cannot start with negative resources or overlapping stacks beyond the limits).

## Security regression policy

- Every known exploit class gets a quirks-ledger entry (`exploit-fix`) and a named regression test that attempts the exploit and asserts rejection.
- Property tests for ownership isolation and observation hygiene (see `05-testing.md`) run on every context.
- Adding a command requires writing its validation, rejection tests, and visibility scope in the same change. The DoD checklist enforces this.

## Out of scope for the core

Transport encryption, authentication protocols, account management, matchmaking, client integrity/anti-tamper on the client side. These belong to server and client layers; the core only guarantees that a correct server cannot be tricked via valid-looking commands and that it can avoid leaking hidden state.
